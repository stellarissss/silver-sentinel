# 折叠诊断与死站清理（v1.16.3 / v1.16.4）

用户提出两件事：①「同一内容/同一基础设施的网页折叠」为什么没了；②监测运行状况，并把取证失败的资产「最小留痕后删去」，把资源留给继续发掘团伙。本文记录实测结论、根因、改动与生产验收。

---

## 一、折叠「没了」：功能没坏，是可视覆盖率塌了

### 浏览器实测（CDP 驱动真实 Chrome，登录生产控制台，2026-11-09）

| 检查项 | 结果 |
|---|---|
| 后端 `/api/assets` | `collapsed=True`，`1798 条折成 1094 项（41 组同源）` |
| 前端折叠行 | `tr.group-row` 2 行，首行 `pk2n84.cn ×80 同证书` |
| 提示条 / 开关 | 「展开全部（不折叠）」按钮与统计条都在 |
| 展开组 | 点 `▸` 后出现 **80 个成员行**（`open=1`, `memberRows=80`） |
| 关闭折叠 | `groupRows=0`、50 行逐条，按钮变「按同源折叠」；再点恢复 |

结论：**折叠、展开、开关、提示条全部正常**，代码没有回归。截图见 `docs/线索库折叠复测.png`。

### 根因：三条叠加，逐条量化

1. **分组依据全部来自取证成功之后的数据**。`grouping.compute()` 的三类依据分别是 `facts.cert`（同证书）、`facts.backend_hosts`（同收单）、`meta.web_observation.title` + `facts.features.text_len`（同模板）。生产抽样证实：取证成功的资产 `meta` 里有 `web_observation`/`cert`/`group_label`；取证失败的只有 `await_capture`/`hosts`。全库 3731 条无组资产中，`pending 2172 + failed 1233 + dead 94 + captured 232`——**没有正文、没有证书，物理上无从判断「同一内容」**。
2. **新资产 34% 无组**：最近 1 天新增 2538 条，其中 862 条没有 `group_key`。
3. **即使有组，94% 是 1~2 条的小组**：活跃档 850 个组里 797 个 ≤2 条，按 v1.14 的设计不折叠、只标 `+1 同源`，836 条仍逐条平铺；真正 ≥3 条能折的只有 53 组。

所以用户看到的是「一屏 50 行里只有 2 行折叠」，观感等同折叠没了。v1.14 线上实测 46 组里 30 组是「×2 同证书」，全折起来反而更吵，当时已确认「两组以下显示 +1 同源」，本轮保持不变。

## 二、修复：展示层「前缀族」折叠（v1.16.4）

清理死站后活跃档仍有 199 条无组，其中 **164 条来自 `ct_poll`**，样例 `mz479.top`、`gdcr8378.com`、`a3h3g.com` 正是上一轮用 8000 条生产 CT 事件校准出来的「固定字母前缀 + 变数字」长期运营族。它们没有取证正文，但前缀族本身就是**发现期已有的基础设施指纹**。

改动：

- `api.py::_collapse_rows()` 对无 `group_key` 的资产调用 `discover/burst.family_key()`，按 `family:<前缀|TLD>` 临时分组，同样 ≥3 条才折；
- `kind=family`，前端 `kindLabel` 增加「同前缀族」，组标签「同站群前缀族 mz|top」；
- **只影响视图、不写库**，误判可「展开全部（不折叠）」一键绕开；已有 `cert`/`template` 硬证据的分组优先，不被覆盖；
- 测试锁住：同族 4 条折成 1 行、异族与带连字符域名仍逐条、`collapse=0` 关闭、资产表 `group_key` 保持为空、已有 `cert` 组不被覆盖。

生产精确统计（对活跃档全部资产直接跑 `_collapse_rows`，避开 `scan_cap` 截断）：

| 项 | 值 |
|---|---|
| 活跃资产 | 1717 |
| 折叠后行 | 1109 |
| 折叠组 | 54 |
| 判据分布 | `cert 49 / template 2 / backend 2 / family 1` |
| 前缀族组 | `mz464.top` 等 3 条 `mz|top` |
| 无组逐条 | 195 |
| 2 条小组（+1 同源） | 82 |

**如实说明增量有限**：生产活跃档里同族 ≥3 条的只有 1 组，前缀族折叠补上了这一组，但不能把 195 条无组资产全变成分组——它们大多没有可归族的结构化指纹。这不夸大修复效果。

## 四、死站清理：最小留痕后删除

用户授权：「取证失败的可以最小留痕然后删去了，因为已经无需举报，继续发掘团伙/发现新的即可」。

### 安全口径（默认，宁可少删不可误删）

`capture_state ∈ {failed, dead}`，且：

- 无任何 `evidence` / 举报包（取到过东西的站一律保留）
- 无团伙归属、未被人工审阅
- `tier` 不含 `watch`/`confirmed`，`verdict` 不含 `high_risk`

生产 dry-run 964 条 → `--apply` 实删 **965 条**（期间引擎又新增 1 条）：端口无法连接 774、超时 85、NXDOMAIN 22、其它 84；全部落在 `cold 856 / candidate 109`。另外约 **484 条 failed/dead 被自动保留**（有证据 483 / 团伙 65 / 观察档 29 / high_risk 33，有重叠）。

### 三层留痕与可恢复

1. **完整归档**：`/var/lib/silver-sentinel/data/archive/pruned-capture-failed-20261109T143945Z.jsonl`，1.2 MB、965 行，含资产表全部列，可完整恢复。
2. **库内最小留痕**：每域名一条 `DiscoveryEvent(source="asset_pruned")`，记 asset_id、失败原因、档位、判定、发现来源、归档文件名、时间、理由（965 条）。
3. **一键恢复**：`silver-sentinel prune-assets --restore <jsonl> --apply`，按 `normalized` 去重，幂等。

**刻意保留**：历史 `discovery_events` 发现流水（本来就是「这个域名怎么被发现的」记录）、`graph_nodes`/`graph_edges`（IP、证书、ASN 是跨资产的基础设施证据，删掉反而会破坏团伙发现）。

### 级联正确性

- DB `ON DELETE CASCADE` 处理：`capture_tasks`/`signals`/`evidence`/`reports`/`report_bundles`/`asset_snapshots`。
- 手工解引用：`scan_runs`（`NO ACTION`）、`watch_targets`（无 FK）——不然会约束失败或留下悬空引用。
- 生产验收：孤儿 `capture_tasks 0`、孤儿 `evidence 0`、悬空 `watch_targets 0`、悬空 `scan_runs 0`，`asset_pruned` 留痕 965 条，服务 active。

### 命令

```bash
silver-sentinel prune-assets                         # dry-run，默认，只统计不写
silver-sentinel prune-assets --apply               # 归档 + 留痕 + 删除
silver-sentinel prune-assets --include-observed --include-high-risk   # 放宽口径（需显式）
silver-sentinel prune-assets --restore <jsonl> --apply                # 幂等恢复
```

## 五、已知限制 / 下一步

- **折叠**：195 条活跃无组资产仍逐条。要从根上解决，需在入池时把发现期证据（前缀族 key、CT 证书批次）写进 `meta`，或把 `regroup` 挂周期任务；注意 `regroup` 当前会把「无证据资产」的已有 `group_key` 清空，动它之前必须先修这个行为。
- 锁竞争缓解未根治（建图 / 密文化长事务仍撞 `SQLITE_BUSY_SNAPSHOT`）；certstream 单源仍会断流。
- 软件 / APK 侧、短链展开、举报线索、多源 OSINT、模板指纹、收款主体跨站关联仍是空白，是「广泛、较准确搜罗」的主要差距。
- 磁盘 91%，SQLite 未 VACUUM。
- 实时 `burst` 内存态每次重启清零；`discover replay-ct` 是历史补漏通道，可考虑挂周期任务。
