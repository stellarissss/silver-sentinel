# 半自动化举报：把材料准备到「只差点一下」

> 目标：在控制台点一次，证据包自动生成并落到磁盘，浏览器打开对应举报页时字段已经填好，
> 人只需要过验证码、核对、提交。

## 一、先给结论：为什么不做「服务端代提交」

动手前我先去各渠道把表单摸了一遍，结论是**服务端代提交既不可行也不该做**：

| 站点 | 从数据中心直连的结果 | 拦在哪一层 |
| --- | --- | --- |
| `www.12377.cn/jbxzxq/jbxx/smjb.html` | HTTP **521**，返回一段 JS 挑战脚本 | 加速乐（`__jsl_clearance_s`） |
| `www.12377.cn/jbxzxq/jbxx/zcjb/zcjb.html` | 200 | 首页可读，提交仍需登录态 + 图形码 |
| `abuse.cloudflare.com` | HTTP **403** | Cloudflare 自身防护 |
| `www.12321.cn/web` | 200 | 点提交弹**数美滑块**（`Sense.judge`） |
| `urlsec.qq.com/report.html` | 200 | 点提交弹**腾讯防水墙**（TCaptcha） |
| `cyberpolice.mps.gov.cn` | SPA 需登录后才出表单 | 实名注册 + 人脸核验 |

也就是说，凡是能真正下架内容的渠道，都至少有一道「必须是人」的关卡。硬闯等于给对方送风控样本，
还会把举报人身份（我们的出口 IP）暴露出去——这与项目「不暴露自身基础设施」的前提直接冲突。

所以本模块的定位是：**服务端只准备材料，提交发生在举报人自己的浏览器里**。

### 2.1 12377 的真实表单结构

从 `https://www.12377.cn/jbxzxq/jbxx/zcjb/zcjb.html` 抓到的控件：

| 控件 | 名称 | 说明 |
| --- | --- | --- |
| `select#report_platform` | 被举报平台 | `WEBSITE` / `APP` / `ACCOUNT` |
| `select#harm_category` | 危害小类 | 值是小类 32 位 id，**由 cookie `bigHarmType` 决定有哪些选项** |
| `input#website_name` | 网站名称 | ≤40 字 |
| `textarea#website_address` | 网址 | 多行，回车分隔，多行才有效 |
| `textarea#report_content` | 举报内容 | **≤500 字**，超了前端直接截断 |
| `input#upload_file` | 附件 | `multiple`，后缀白名单含 `.pdf` `.zip` `.png` |
| `input#verify_code` | 验证码 | 图片来自 `new.12377.cn/rpapi/portal/captcha` |
| `button` | 提交 | `onclick="submit_reportinfo()"` |

提交接口：`POST https://new.12377.cn/rpapi/portal/report/add`（multipart），
需先 `GET /rpapi/portal/user/get` 拿实名信息，`code=3203` 表示未登录会跳 `/Login.html`。

**关键坑**：`#harm_category` 的选项是页面加载时按 cookie `bigHarmType` 动态生成的。
所以扩展必须先写 cookie 再开页面，否则下拉是空的——我们把它放在 `pre` 步骤里，先于一切填充。

## 三、实现结构

```
服务端                                    浏览器
─────────────────────────────────         ────────────────────────────
report/channels.py   渠道注册表
report/harmtype.py   类别判定 ──┐
report/narrative.py  正文生成   ├─→ POST /api/report/build
report/bundle.py     证据包     │      ↓
report/fill.py       填表载荷 ──┘   fill.json（动作清单）
                                        ↓
                                  扩展 background：设 cookie、开标签页
                                        ↓
                                  content/filler.js：按 selector 执行动作
                                        ↓
                                  人：过验证码 → 核对 → 提交 → 点「登记回执」
```

**扩展只认动作，不认网站**。动作原语有 8 个：`cookie` `wait` `select` `radio` `check` `fill`
`attach` `highlight` `auto_label`。渠道改版时改服务端 `fill.py`，不必重发扩展。

### 3.1 证据包长什么样

一次生成三份产物，落在 `data/report_bundles/<code>/`：

| 文件 | 用途 |
| --- | --- |
| `<host>-举报材料-<code>.pdf` | 人读。封面信息表 + 正文 + 判定依据 + 证据清单 + 截图 + 校验方法 |
| `<host>-证据包-<code>.zip` | 提交附件。PDF + 截图 + HTML 原文 + 正文快照 + `manifest.json` + `manifest.sha256` |
| `manifest.json` | 逐文件 SHA-256 + 证据链首尾哈希 |

截图统一压到 1100px 宽（JPEG 82），HTML 超过 4MB 截断并在 manifest 里标 `truncated`——
**宁可标注截断，也不静默丢数据**。

### 3.2 正文怎么保证「可信」

三条规则写在 `narrative.py` 顶部，也落实在测试里：

1. **只写能核查的事实**。IP、注册商、备案、存活天数、截图张数全部来自采集数据；缺失就不写。
2. **不做定性**。用「涉嫌」「请核查」，结论留给有权机关。
3. **引号里只能是页面原话**。从 `page_text` 证据里按词根打分摘句，含「常见于/说明/可能/往往」
   这类主观推断的句子直接过滤——这类句子是材料被退回的常见原因。

500 字上限下，裁剪顺序是：先保「对象 + 诉求」，再依次塞「页面原文 → 行为 → 经过 → 证据」。
测试 `test_brief_respects_limit_and_keeps_demand` 就是守着这条。

实际产出（测试样本）：

```
【对象】网站「guohui-yanglao-bt.cn」，解析 IP 45.132.77.19，注册商 Alibaba Cloud Computing Ltd.。
【页面原文】“补贴申领登记：姓名、身份证号、银行卡号、手机验证码”；“国家惠民养老补贴申领中心”
```

## 四、怎么用

1. 装扩展：`chrome://extensions` → 开发者模式 → 加载已解压的扩展程序 → 选 `extension/` 目录。
2. 扩展「设置」里填哨兵地址（默认 `http://127.0.0.1:18700`）；服务端设了
   `SILVER_REPORT_EXTENSION_TOKEN` 就同时填令牌。
3. 控制台 → 线索库 → 点开目标 → 「一键举报」→ 选渠道 → 可改正文 → 「生成证据包并打开举报页」。
4. 举报页打开后字段已填好，右下角悬浮条列出「还需你完成」的步骤。
5. 提交后点悬浮条上的「已提交，登记回执」，回执号写回 `report_bundles.receipt`。

没装扩展也能用：点按钮会下载证据包、复制正文、打开举报页，手动粘贴即可。

## 五、边界

- **不代提交**。没有任何自动点「提交」的代码路径，验证码永远留给人。
- **不绕验证码**。数美滑块、腾讯防水墙、Turnstile、加速乐 JS 挑战一律由人完成。
- **不伪造材料**。正文只引页面原话，截图是采集时的真实渲染，哈希可校验。
- **不留我方痕迹**。证据包不含采集端主机名、出口 IP、内部路径；`report_api_base` 只出现在扩展载荷里。
