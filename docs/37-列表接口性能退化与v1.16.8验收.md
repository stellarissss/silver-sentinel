# v1.16.8 · `/api/assets` 挂死根因、修复与生产验收

承接 [docs/36](36-失联折叠与新线索取证饥饿.md)。v1.16.7 把失联站点折叠做完后，
部署到生产出现一个「一个接口正常、另一个接口挂死」的故障：`/api/stats` 200，
但 `/api/assets` 连续 60s / 150s 返回 `HTTP 000`，服务日志里没有任何
Traceback。本文记录定位过程、根因、修复，以及失联折叠的最终生产验收。

## 1. 现象

| 请求 | 结果 |
|---|---|
| `GET /api/ping` | 200 / 0.03s |
| `GET /api/stats` | 200 / 4.2s |
| `GET /api/assets?collapse=0&limit=12` | 200 / 8.2s |
| `GET /api/assets?limit=12`（默认 `collapse=1`） | **HTTP 000 / 150s 超时** |

服务进程 active、端口 `0.0.0.0:18700` 正常监听、线程数 31，日志里 DNS 探测、
研判周期 #10/#11、重评都在持续输出，没有 ERROR。也就是说 Web 进程活着，
只有这一条路由拿不到线程执行时间或直接卡死。

## 2. 定位：先切分边界，再计时

**第一步排除路由/中间件。** 未登录状态下逐个 curl，`/api/ping` 200，其余
（含 `/api/assets`）全部 0.0005s 秒回 401 `{"detail":"未登录或会话已过期"}`。
说明请求正常进了路由，问题在鉴权之后的函数体内部。

**第二步锁定分支。** 登录后对比：`collapse=0` 能返回，`collapse=1` 挂死。
两个分支唯一的差别是折叠分支会 `list(session.scalars(stmt))` **全量取行**，
非折叠分支只 `.offset().limit()` 取 12 行。

**第三步在生产 Python 里分段计时。** 这里踩过一个坑：独立进程不带
`/etc/silver-sentinel.env` 时连的是默认空库，测出来「资产 0、证据 0、耗时 0s」，
完全是假数据。必须 `set -a; . /etc/silver-sentinel.env; set +a` 后再测。
真实数据：`Evidence` 57592 条、active 档资产 4637 条。

| 阶段 | 耗时 | SQL 次数 |
|---|---|---|
| 裸全量 ORM（4637 行） | 3.66s | 1 |
| **全量 + `selectinload(Asset.evidence)`** | **53.35s** | 22 |
| `_asset_row()` 逐行 4637 次 | 5.02s | 累计 170 |
| `_collapse_rows()` | 0.20s | — |

## 3. 根因

v1.16.6 为了消掉「列表 50 行各查一次证据」的 N+1，把
`stmt.options(selectinload(Asset.evidence))` 加在了**无条件**的 `stmt` 上。
这对「只取 50 行」的非折叠视图是划算的；但折叠视图为了按 `group_key` /
前缀族分组并保证 `total` 是全局折叠后的项数，必须取全量 4637 行——
于是 57592 条 `Evidence` 被一次性 ORM 化，光这一步就 53s。

再叠加两层放大：

- `_asset_row()` 会读 `asset.campaign`，折叠路径对全量行逐条调用它，
  触发约 148 次懒加载查询（SQL 从 22 涨到 170）；
- uvicorn 是单进程，`def` 同步路由跑在 AnyIO 线程池里，同一进程还跑着
  取证 worker、CT 轮询、研判周期（实测单周期 17–22s），GIL 竞争把 50s
  量级的 Python 侧工作继续放大到 150s+ 不返回。

所以这不是「代码慢一点」，是**一个分支正确、另一个分支把整张证据表灌进内存**。
`collapse=0` 之所以正常，纯粹因为它只取了 12 行。

## 4. 修复

折叠视图每行只需要一个 `evidence_count` 数字，不需要 `Evidence` 对象：

1. **一次聚合下推到 SQL**，条件与 `Asset.evidence` 的 `primaryjoin`
   （`Evidence.deleted_at IS NULL`）保持一致，软删 tombstone 不计入：

   ```python
   evidence_counts = {
       int(asset_id): int(n)
       for asset_id, n in session.execute(
           select(Evidence.asset_id, func.count(Evidence.id))
           .where(Evidence.deleted_at.is_(None))
           .group_by(Evidence.asset_id)
       ).all()
   }
   ```

2. 折叠分支不再加载 `evidence` 关系，改为 `selectinload(Asset.campaign)`
   一次预加载，消掉 `campaign` 的 N+1。
3. `collapse=0` 分支保留原来的按需 `selectinload(Asset.evidence)`。
4. `_asset_row(asset, evidence_counts=None)` 与
   `_collapse_rows(rows, fold_offline=..., evidence_counts=None)` 增加可选参数并透传；
   不传时走原 relationship 路径，既有调用方与测试零改动。

改动文件：`src/silver_sentinel/api.py`。

## 5. 防回归

新增 `tests/test_assets_fold_perf.py`（3 例）：

- 折叠 / 非折叠两条路径的 `evidence_count` 一致，且排除软删证据；
- **核心**：监听 `Session.loaded_as_persistent`，断言折叠请求期间没有任何
  `Evidence` 实例被 ORM 加载（构造 300 条证据放大场景），并自检监听器确实生效，
  避免断言恒真的假阳性；
- 失联大组走同一条计数路径，成员截断不丢 `evidence_count`。

做过一次**反向验证**：临时把 `selectinload(Asset.evidence)` 加回折叠分支，
`test_fold_never_loads_evidence_orm` 如期失败；恢复源码后 3 passed。
这条测试确实能挡住退化，不是摆设。

全量 `557 passed`、`ruff check src tests` 全清、`node --check app.js` 通过，
wheel 内容校验确认聚合计数、软删过滤、`campaign` 预加载、两条分支的加载方式
都已打包。

## 6. 生产验收（v1.16.8）

部署 `silver_sentinel-1.16.8-py3-none-any.whl`，健康检查 `/api/ping` 通过。

| 接口 | 修复前 | 修复后 |
|---|---|---|
| `/api/assets?limit=12` | HTTP 000 / 150s | **200 / 6.66s** |
| `/api/assets?limit=50` | — | 200 / 6.21s |
| `/api/assets?collapse=0` | 200 / 8.2s | 200 / 4.21s |
| `/api/assets?fold_offline=0` | — | 200 / 6.21s |

折叠统计：`total=2414`、`raw_total=4639`、`offline_count=967`、
`group_count=178`；`evidence_count` 有真实值（119 / 17 / 14 …），聚合口径正确。

**CDP 真实浏览器前后对比：**

- 概览页「风险最高线索」修复前全是 95 分失联站群 `pk2n84.cn` / `v7qm28.cn`；
  修复后是 `zqtn56.com.cn` 等活跃 `captured` 站（带「取证 119 件」），
  并出现提示条「另有 967 条失联站点…已从本榜折叠，证据与判定仍保留」。
- 线索库首屏修复前是 `pk2n84.cn ×80 同证书 / 站点失联`；修复后是
  `zqtn56.com.cn ×9 同证书`，顶部显示 `10349 条折成 7252 项（256 组）`、
  `1441 条失联站点已折叠`，蜜罐 / ＋1 同源标记完整。
- 最后一页（offset 2402）全是 `offline=True` 的组，且 `kind=family` / `cert`
  保留、`size=14` 等同源依据没有被吞掉——折叠是沉底，不是删除。
- `fold_offline=0` 时 `offline_count=0`、无 offline 标记；前端「展开全部
  （不折叠）」按钮切成 `共 10354 项` 全量视图，开关可绕开。

**「为何这么长时间没有新发现」的最终答案：**

| 层 | 实测 | 结论 |
|---|---|---|
| 发现 | 近 24h 新增资产 1868 条 | 没停 |
| 取证 | 近 24h `captured` 2048 条、`failed` 7 条；队列 done 9756 / queued 16 / running 1 | 吞吐正常，无积压 |
| 新线索 | 近 24h 新增 active 档 1214 条，其中 450 条仍 `pending` | 在排队消化，不是零 |
| 展示 | 修复前按 `score desc` 前 60 行 100% 是 `dead`/`failed` 高分站 | **真因：新线索被压到后面** |

也就是说发现层与取证层一直在跑，用户看到的是「展示层被已举报的失联高分站
占满 + 新线索取证前 0 分按分数排序必然沉底」。折叠修复后首屏换成活跃站，
但新线索仍要等取证才有分数——若要看最新入库，应在线索库按 `first_seen`
排序，或后续补一个「最新发现」快捷视图。

`backfill()` 的 `fresh_rank` 修复在生产已生效：近 3h 新建 407 个
`CaptureTask`，其中 `reason=backfill` 277 个、`watch` 130 个；最新 12 个
近 24h 资产里 4 个已经 `captured` 并产出 6–7 条证据，其余是刚入库、
下一轮才补队的 `pending`。

## 7. 已知限制 / 下一步

- 列表仍约 6s，不是本次代码路径的退化，而是 DB 层：`sentinel.db-wal` 约
  44MB、磁盘 91%、折叠仍要把 4639 行 ORM 化。彻底做法是把分组阶段改成
  **只查轻量列**（`id/value/score/tier/capture_state/group_key/...`），
  仅对当前页的代表行回表取完整字段；本轮先保证可用性，未一并改动。
- `/api/stats` 同样约 6s，同源问题，一并纳入上面的优化。
- `fold_offline` 按 `dead` + `failed` 判定，`failed` 里混着「站点还活着但
  取证超时」，后续按 `capture_error` 细分（见 docs/36 第 5 节）。
- 发现质量的结构性差距（CT 流里大量无关 SAN、外部情报源弱）未在本轮处理，
  不能靠改兜底阈值「悄悄」抬门槛来粉饰。
- capture 340 行长事务未拆分；`chain_anchors` 仍为人工登记；reports 仍 0；
  真正异地备份尚未配置。
