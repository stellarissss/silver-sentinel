# 卡死复发：内存颠簸（swap thrashing）根因与根治 — v1.16.11

日期：2026-11-21

## 现象

用户反馈服务再次卡死：`/login` 15s 超时、`/api/ping` 26s、主页加载不出来。

## 与上次卡死的区别

| | 上次（v1.16.9 修复） | 本次（v1.16.11 修复） |
|---|---|---|
| 根因 | Playwright 浏览器进程泄漏（孤儿 chromium 堆到 51 个） | 内存耗尽 → swap 颠簸（磁盘 IO 饱和） |
| 性质 | 进程没回收 | 内存容量 + 失败站反复触发重型取证 |
| v1.16.9 机制 | 修复它 | 正常工作，非本次根因 |

## 取证证据（生产实测）

| 指标 | 数值 | 含义 |
|---|---|---|
| 物理内存 | 1.96G，可用仅 125MB | 见底 |
| 主进程 RSS | 1.4G（71%） | 单进程吃掉大部分 |
| swappiness | 100（默认 60） | 系统极度激进去 swap |
| swap 换页 si/so | 峰值 12 万 KB/s | 教科书级颠簸 |
| major page faults | 1444 万次 | 反复从磁盘换页 |
| 磁盘读 | 25MB/s 持续 | iowait 顶到 51-54% |
| 磁盘占用 | 97%（仅剩 1.6G） | IO 竞争恶化 |

## 因果链

1. 低质失败站 `8cc145.cc`（26.6 分、failed）的失败文本是「取证超时，已重建执行线程」；
2. `classify_failure()` 不含该标记 → 归为 `FAILURE_TRANSIENT`，**只冷却 10 分钟**；
3. 10 分钟后该站重新入队 → 拉起 Chromium → 卡满硬超时 150s → 重建线程 → 再拉起新 Chromium；
4. 每次重建峰值几百 MB，28 个同类站循环往复 → 内存跌破水位；
5. swappiness=100 触发疯狂换页 → iowait 54% → 整个 Python 进程被 IO 阻塞 → 连 ping 都要 26s → 用户视角「卡死」。

**一句话**：一个被错误分类的超时失败，让卡浏览器的站每 10 分钟就重启一次 Chromium，反复把 2G 内存推入颠簸。

## 修复（v1.16.11，代码根治）

| # | 文件 | 改动 |
|---|---|---|
| 1 | `capture.py` | 新增 `FAILURE_STALL` 类别，识别线程级超时/重建文本；冷却复用判死时长（48h），首次失败即落 `failed` 不做分钟级重试。普通页面 goto 超时仍归 transient，不受影响。 |
| 2 | `capture.py` | 单次取证硬超时 `_CAPTURE_TIMEOUT` 从 150s 收紧到 **90s**，卡死危害窗口砍掉 40%（仍覆盖 45s 沙箱 + 大包下载 + 两张截图）。 |
| 3 | `sandbox/web.py` | 首屏与全页截图加显式 `timeout`（≤12s）——截图是少数不受 `set_default_timeout` 约束、能钉死取证线程的操作。 |
| 4 | 测试 | 新增 STALL 分类断言、长冷却（≥瞬时 100 倍）与硬超时上限回归测试。 |

## 止血动作（生产机，一次性）

1. 删除 chess 遗留归档 `/root/game-chess-archive-20261025`（2.3G），磁盘 1.6G→3.8G；
2. `vm.swappiness` 100→10 并写入 `/etc/sysctl.conf` 持久化，减少换页倾向；
3. `systemctl restart silver-sentinel` 打破已形成的颠簸螺旋。

止血后：login 0.17s、ping 0.25s、stats 4.7s，可用内存 125MB→353MB。

## 验收

- 相关测试 20 passed；全量 571 passed（另有 1 个既有 flaky 测试 `test_burst::test_family_cooldown_accumulates_instead_of_dropping` 在改动前后均失败，与本次无关，`cooldown=999999` 依赖时间戳）；
- ruff 全过；
- 生产部署后观察：STALL 类失败落 48h 冷却，不再反复拉起 Chromium；硬超时 90s 内回收。

## 长期约束与建议

- 机器仅 1.9G 内存是长期瓶颈：取证 Chromium 峰值几百 MB + API + 后台发现并发，必然吃紧。根治靠代码降低单次冲击（本次已做），彻底解决仍需**扩容内存或迁移**（用户本次选择仅做代码优化，硬件建议留作后续决策）。
- `vm.swappiness=10` 已持久化，重启不失效。
- 卡死站不丢弃证据、不删资产，只是拉长取证冷却，仍会周期性复查。
