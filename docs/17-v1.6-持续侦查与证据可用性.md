# 17 · v1.6：持续侦查与证据可用性

> 这一版解决的是一句质询：「这么长时间，为什么没有发现任何高价值线索？」
> 结论不是"没抓到"，而是**抓到了却读不出来**。

## 一、实测到的断链

v1.5 部署后，线上库的样子：

| 指标 | 数值 | 说明 |
| --- | --- | --- |
| 资产总数 | 3173 | 发现层在正常工作 |
| 取证成功的资产 | 145 | 页面确实打开过 |
| 真正落盘 `page_text` 的 | 58 | Chromium 渲染成功 |
| 有正文且分数 ≥ 40 的 | 0 | **异常** |
| 证据记录 | 2378 | |
| 明文还在的 | 41 | 其余 2339 条被证据仓脱敏 |
| 脱敏且有本地密文的 | 2359 | 数据没丢，只是没人读得出来 |

三层原因，逐层叠加：

1. **读不到正文**。`SILVER_VAULT_REMOVE_PLAINTEXT=1` 会在加密后删掉明文；
   而所有读取方（预览、下载、打包、重扫）都是 `Path(row.path).read_bytes()`，
   文件不在就 `except OSError: text = ""`。取证做得再多，研判拿到的还是空串。
2. **评分不重算**。取证结束时只调了 `triage.apply`，没有用页面正文重新 `assess`。
   分数仍是发现层落库时的口径——只看域名，上限
   `1-(1-0.182)(1-0.252)=38.8`，永远够不到 `WATCH_SCORE=50`。
3. **吞吐不连续**。取证是主周期的第 3 步：建图 40 秒、富化 20 秒、取证 45 秒，
   一轮两分钟，实际取证速率只有设计的 1/3；任何一步卡住，取证全停。

用密文解出 70 条历史证据重算验证：平均 **+11.3 分**，21 条进入 50–70 区间，
最高 64.6。分不是不够，是从来没算过。

## 二、这一版做了什么

### 1. 证据只有一个读取入口

`evidence.py` 新增 `read_bytes / read_text / read_status / materialize`：
先读明文，读不到就用 `sha256` 从本地密文还原。所有调用方都改过来了：

- `GET /api/evidence/{id}/preview` —— 界面不再显示"文件已丢失"
- `GET /api/evidence/{id}/download` —— 密文解密到 `data/tmp/` 再下发
- `GET /api/assets/{id}/evidence.zip` —— 证据包里真的有文件
- `pipeline._scan_one` —— 研判能读到正文
- 变更检测 / 重评 —— 同上

> 仍然遵守「脱敏」的初衷：解密只发生在内存或临时目录，不写回 evidence 目录。

### 2. 取证后立刻重算评分

`scoring/reassess.py`：取证拿到正文后，用完整 facts + 正文重跑规则评分，
回写 `score / confidence / verdict` 与信号表，再走分级。

幂等键是**正文证据 id**：同一条正文不重复重算；只有新取证产生了新证据才重评。
这条规则同时解决了「流水线每小时把同一批资产重算一遍」的隐患。

### 3. 取证独立成常驻线程

```
调度线程   每 60s：研判 → 富化 → LLM 补判 → 建图
取证线程   常驻：抓到一条立刻抓下一条，队列空了才退避到 15s/60s
巡检线程   每 30min：清任务台账 / 临时文件 / 回收站，检查磁盘
看门狗     每 60s：线程死了重拉；调度与发现引擎也一并检查
```

主周期不再碰 Chromium。回填优先级：已确认 > 高度可疑 > 候选，同档按分数降序；
已取证资产超过 `SILVER_CAPTURE_REFRESH_HOURS`（默认 72 小时）会重新排队。

### 4. 卡死自愈

- 单次取证硬超时 600s → **240s**，超时后重建取证线程（Playwright 卡住时，
  旧实现会让整条队列一直排在它后面，直到进程重启）；
- 进程重启遗留的 `running` 任务 15 分钟后回收为 `queued`；
- `TaskRun` 只留最近 3000 条，避免长期运行把库撑大。

### 5. 日志终于写得出来

项目里所有模块都用 `logging.getLogger`，但从来没有 `basicConfig`——
INFO 级别的「周期完成 / 取证成功」全部进了黑洞，只剩 WARNING 和 Traceback。
现在控制台 + `data/logs/silver.log`（20MB × 5 滚动）双通道，第三方库降噪。

### 6. LLM 真正参与

- 送模型的不再只有摘录，还带**证据编号列表**；
- 模型输出的 `[E:12345]` 会与真实证据 id 核对，幻觉编号单独记账；
- 调用失败不再静默：401 / 404 / 402 的原因会写进日志；
- token 用量记进 `meta.llm.usage`；
- 每轮补判 2 条 `SILVER_LLM_BATCH`，只挑「有正文、还没判过」的灰区资产，
  失败后有 6 小时冷却；
- 模型结论只作为**分级信号**（`urgent` / 一条硬证据），不改分数——分数必须可复核。

### 7. 其他

- 安装包线索：DOM 找不到时，从运行时请求与 HTML 里再捞一遍 `.apk`；
- pivot 噪声域名扩充（akamaihd / wsimg / afternic / wps 静态资源等），
  减少「回灌了一个 CDN」；
- 新增 `GET /api/health/self`：线程存活、心跳年龄、队列积压、成功率、磁盘；
- 新增 `POST /api/ops/rescore`、`POST /api/assets/{id}/llm` 与 `silver-sentinel rescore`。

## 三、新增配置

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `SILVER_CAPTURE_INTERVAL` | 15 | 队列空时的轮询间隔（秒） |
| `SILVER_CAPTURE_REFRESH_HOURS` | 72 | 已取证资产的复访周期 |
| `SILVER_CAPTURE_BACKFILL` | 8 | 每次补队上限（仍受水位约束） |
| `SILVER_LLM_BATCH` | 2 | 每轮 LLM 补判条数，0 表示关闭 |

## 四、上线后怎么验

```bash
# 1. 自检：线程、队列、磁盘
curl -s localhost:18700/api/health/self | jq '{ok,problems,cycle,capture,disk}'

# 2. 证据读得出来（挑一条历史证据）
curl -s "localhost:18700/api/evidence/<id>/preview" | head

# 3. 批量重评历史资产
silver-sentinel rescore --limit 2000
#    关注输出里的 changed / upgraded

# 4. 分数分布（应出现 50+）
sqlite3 /var/lib/silver-sentinel/data/sentinel.db \
  "select case when score>=70 then '70+' when score>=50 then '50-70'
               when score>=40 then '40-50' else '<40' end band, count(*)
   from assets where score>0 group by band;"
```

判定「持续侦查」是否成立，看三个数：

- `capture.oldest_queued_minutes` 不再单调增长；
- `capture.success_rate_recent` ≥ 0.8；
- `heartbeats.cycle.age_s` < 300。
