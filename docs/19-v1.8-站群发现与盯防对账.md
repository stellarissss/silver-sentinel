# v1.8 站群发现与盯防对账

v1.7 解决的是「取证别停」。v1.8 解决的是另外两个更隐蔽的问题：
**该发现的没发现**，以及**该盯的没人盯**。

两条都是「指标全绿、实际没干活」的类型，靠看 dashboard 发现不了。

---

## 一、两个线上事实

### 1. `watch_targets` 是空的，`scan_runs` 一天 0 条

```
watch_targets  []
scan_runs 24h  0
assets tier    watch 1 条
```

分级升到 watch 之后要「纳入周期盯防」，这个调用散落在 intake、rescore、
人工三处。任何一处漏掉（或历史上某次异常中断），资产就只剩「24 小时复访」
这一档低频动作——**看起来在跑，实际没人盯**。

这类失效不会报错，也不会让心跳停：`/api/health` 全绿，`due=0` 也解释得通
（本来就没目标要跑）。

### 2. 新资产 22 条/小时，且几乎全是 0–10 分

```
new assets 1h/6h/24h   [29, 130, 654]
score 分布  0分 897 / 10分 429 / 20分 130 / 30分 47 / 40分 4 / 50分以上 0
```

发现链路没有坏，是**门槛把该收的收掉了**。词库的折算规则是：

> 没有「强簇」（冒充机构 / 骗局黑话 / 冒用品牌）时，其余簇乘 0.30。

于是 `fupin-zhongxin.cn`（扶贫中心）算出来 `0.55 × 0.30 = 0.165`，
连 0.30 的落库门槛都过不去，直接被丢。而「域名里写扶贫/养老/补贴」的站，
恰恰是最该盯的一类。

`butie-fafang.cn`（补帖发放，故意写错字绕审查）`0.60 × 0.30 = 0.18`，同样被丢。

## 二、证书级关联：一张证书就是一条团伙线索

CT 日志里每条记录都带完整证书，一张证书通常有 10–30 个 SAN。以前只把
SAN 当成「同一个域名的不同主机名」，全部 collapse 掉；现在把它当成**关联证据**。

三个层次，成本从低到高：

| 层次 | 判据 | 成本 | 用途 |
| --- | --- | --- | --- |
| 同证书扩散 | 同一张证书上的其他注册域 | 零（数据已在手） | 兄弟站还没建站也能进池 |
| 同批签发 | 一批里 ≥2 个域名共用证书 | 零 | 一次签给整个站群，最早能看到 |
| 同指纹回溯 | 库里已有同指纹的可疑资产 | 一次批量查询 | 跨时间的站群归并 |

实现上散在 `_spread_cert_siblings()` 与 `_persist()`：

- **扩散门槛不是分数，是簇**。域名命中分数普遍在 0.16–0.30，用 0.5 卡
  等于永远不扩散；但只看分数又会让载体词（中心/平台/客服）把整张证书的
  无关域名全捞进来。判据改成「至少命中一个强簇」：
  `policy_theme / authority / elder_care / scam_signature / inducement / variant`。
- **每张证书最多扩散 8 个**，防止一次签发 200 个泛域名把池子刷爆。
- 兄弟域名用 `san:` 前缀独立去重，避免「先以冷档进来，之后自己命中关键词
  反而被挡在门外」。
- 兄弟进的是冷档（hint 0.28，低于 0.30 门槛），不跟真线索抢取证队列。
- 来源单独标 `ct_san`，事后能分清是词库捞到的还是证书带来的。

同批签发与同指纹回溯会在 `discovery_reason` 里写明「同批签发 N 个域名」或
「同证书：xxx」，人工复核时一眼能看到为什么收它。

## 三、词库折算修正

只改两处，都是「把该保留的留住」：

| 簇 | 无强簇时折算 | 改前 | 理由 |
| --- | --- | --- | --- |
| `policy_theme` | 0.55 | 0.30 | 0.55×0.30=0.165，过不了 0.30 门槛；扶贫/养老/补贴类域名全被丢 |
| `variant` | 0.75 | 0.30 | 错别字是**主动规避审查**的行为，不是无害的相关词 |

改后：

```
fupin-zhongxin.cn   0.165 → 0.3025   刚好过门槛，进冷档
butie-fafang.cn     0.18  → 0.55     进候选，可按证书继续扩散
```

冷档不立刻取证，只进池等填谷；所以覆盖面变大，但浏览器负载不变。

## 四、机构级伪装

线上 `tuiyijunren.cn`（退役军人网）46.6 分卡在 watch 门外：

```
coverage      {impersonation: 3}
content_rules IMP-001, KW-004, CT-003
keyword_hits  21 个
text_len      4439 字
```

原有的结构旁路要求「冒充 + 说服」同时成立，而它没有说服类特征。但一次
伪造三个身份元素（部委名、公文格式、证件样式）本身已经足够定性——这类站
往往正文稀疏（大量图片、PDF 附件），加权分永远上不去。

新增判据：

```python
IMPERSONATION_WATCH = 3
if impersonation >= IMPERSONATION_WATCH and score >= WATCH_SCORE_COMPOSITE:  # 45
    → watch
```

对照 `zijinpan.cn`（资金盘曝光网）`impersonation=1`，仍留在候选池，不会被这条
规则误捞。

## 五、盯防对账

`reconcile_watch()` 在 housekeeping（30 分钟一次）里跑：把 tier 为
watch/confirmed 的资产逐条对上 `watch_targets`，缺的补上，`next_run_at`
设为 5 分钟后（对账发现的漏网目标通常已经很久没被看过）。

只在配额内补（`MAX_AUTO_WATCH=200`），不淘汰已有目标——对账的职责是补齐，
不是重新排座次。

## 六、发现产能

| 参数 | 改前 | 改后 | 说明 |
| --- | --- | --- | --- |
| `ct_poll_logs_limit` | 3 | 5 | 3 条日志覆盖不到全球新增证书的 5% |
| `ct_poll_interval` | 60 | 30 | 轮询是「预算内尽量追平」，间隔只决定歇多久 |
| `ct_poll_batch` | 256 | 384 | 单页条数，影响追平速度 |
| pivot 单次回灌 | 12 | 30 | 落地页外链是滚雪球的主要来源 |

> 部署机是 2 核 1.9G。CT 轮询是 IO 密集，5 条日志的 CPU 占用 < 5%；
> 若 RSS 持续上涨再降回 4 条。

**注意**：`/etc/silver-sentinel.env` 里若有显式 `SILVER_CT_POLL_LOGS_LIMIT`
会覆盖代码默认值，升级时需同步改。

## 七、`brief` 命令

```bash
silver-sentinel brief --hours 24
```

```
侦查态势（近 24 小时）
  新资产      654   ct_poll 78  pivot 52
  证书兄弟     34   同证书扩散（站群关联）
  取证完成    166   失败 12（成功率 93.3%）
  新增证据    285
  新增盯防      1
  待取证        0   队列里还排着的资产
```

三条自检规则，任一命中就返回 1（可挂到监控）：

- 没有新资产、也没有待取证 —— 发现链路可能停了；
- 有待取证但没有完成 —— 取证线程可能卡住；
- 失败数超过完成数 —— 目标侧集体拒连，检查出口 IP 是否被拉黑。

## 八、心跳与 `doctor`

`heartbeat.json` 增加 `discover` 段：`running / lag / frozen / seen / queued /
cert_siblings / cert_cluster`。

`doctor` 的判据保持保守：

- `discover.running == false` → 算故障，看门狗重启；
- `lag > 300000` → 只写 `discover_warning`，**不触发重启**（重启解决不了产能，
  反而丢游标）。

## 八点五、上线即修：预检误杀与异常高的失败率

1.8.0 上线 5 分钟，`brief` 报「失败数超过完成数」（32 完成 / 34 失败，成功率
48.5%）。失败明细里有 45 条「端口无法连接（HTTP/HTTPS 均不通）」、21 条
「Timeout 12000ms」。

两个都是自己埋的：

| 问题 | 原因 | 修法 |
| --- | --- | --- |
| 端口预检误杀 | 3 秒单次连接，跨境链路 RTT 高时必然超时 | 5 秒 + 重试一次 |
| 误判的代价太大 | 「端口不通」被归为 dead，冷藏 72 小时 | 归为 blocked，24 小时重试 |
| 重试超时太短 | 1.7.6 把重试预算压到 12 秒，慢站直接二次失败 | 20 秒 |
| dead 冷却太长 | 新域名常要一两天才建站，72 小时等于判死刑 | 48 小时 |

判据不变的部分：**只认明确的 NXDOMAIN 才算 dead**。端口不通、超时、空响应
一律归到 blocked / transient——多试一次的代价是几十秒，误杀的代价是线索消失
一两天。

`tests/test_capture_dead_targets.py` 补一例钉住这个口径。
