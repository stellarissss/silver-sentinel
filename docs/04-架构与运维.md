## 一、数据流

```
                        ┌──────────────┐
   链接 / 域名 / APK ──▶ │  normalize   │  URL 去追踪参数、域名取可注册域、指标抽取
   文本 / 小程序名       └──────┬───────┘
                                ▼
                        ┌──────────────┐
                        │  collectors  │  只读被动情报，不访问目标站点
                        └──────┬───────┘
              ┌─────────────────┼─────────────────┐
              ▼                 ▼                 ▼
        crt.sh / RDAP     URLhaus / OpenPhish   APK 静态解析
        DNS 变体探测      官方通报清单匹配       AXML/权限/证书/模板指纹
              └─────────────────┼─────────────────┘
                                ▼
                        ┌──────────────┐
                        │    scoring   │  声明式规则求值 → noisy-OR 聚合 → 弃权判定
                        └──────┬───────┘
                                ▼
                        ┌──────────────┐
                        │  analyzers   │  LLM 叙事（可弃权） / Union-Find 团伙归并
                        └──────┬───────┘
                                ▼
        ┌───────────────────────┼───────────────────────┐
        ▼                       ▼                       ▼
   assets/signals           evidence                campaigns
   （线索与依据）           （哈希链）              （团伙聚合）
                                ▼
                        ┌──────────────┐
                        │   respond    │  举报材料 / 一页纸
                        └──────────────┘
```

每次扫描都是幂等的：同一对象重复扫描只累加 `scan_count`，信号整体重写，不会堆积重复行。

## 二、模块职责

| 模块 | 职责 | 关键约束 |
| --- | --- | --- |
| `config.py` | 环境变量与 `.env` | 敏感值只从环境读，不进日志 |
| `normalize.py` | 规范化与指标抽取 | 零宽字符清除、URL 去参、Luhn 校验 |
| `models.py` | SQLAlchemy 2.0 模型 | 资产 `(kind, normalized)` 唯一 |
| `db.py` | 会话、WAL、证据链校验 | SQLite 开 `foreign_keys`、`busy_timeout` |
| `scoring/engine.py` | 规则求值 + 聚合 | 单条规则异常不中断整次研判 |
| `collectors/apk.py` | APK 静态分析 | 自实现 AXML 解析，失败降级正则 |
| `analyzers/llm.py` | LLM 研判 | 严格 JSON 校验 + 脱敏 + 弃权 |
| `analyzers/cluster.py` | 团伙归并 | Union-Find，结果幂等 |
| `intake.py` | 扫描编排 | 采集失败不影响规则判定 |
| `respond.py` | 举报材料 | 只陈述事实，不做法律定性 |
| `monitor.py` | 调度 | 数据库存 `next_run_at`，多实例安全 |
| `api.py` / `web/` | 控制台 | 无构建步骤，零 node 依赖 |

## 三、存储

默认单文件 SQLite（WAL 模式）。

| 项 | 位置 | 说明 |
| --- | --- | --- |
| 数据库 | `data/sentinel.db` | 线索、信号、证据元数据、举报草稿 |
| 证据文件 | `data/evidence/<sha256>.<ext>` | 内容寻址，天然去重 |
| 官方清单 | `data/official_watchlist.yaml` | 可选覆盖，缺省用包内置版本 |

**备份**：只需备份 `data/` 整个目录。

```bash
sqlite3 data/sentinel.db ".backup 'data/backup-$(date +%F).db'"
tar czf evidence-$(date +%F).tar.gz data/evidence
```

**切 Postgres**（线索量 > 10 万或需要多人并发时）：

```bash
pip install "psycopg[binary]"
SILVER_DB_URL=postgresql+psycopg://user:pass@host/sentinel silver-sentinel serve
```

表结构由 SQLAlchemy 自动创建，无需迁移脚本。

## 四、部署

### 单机（推荐起步）

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -e .
silver-sentinel serve --host 127.0.0.1 --port 8000
```

systemd 单元：

```ini
[Unit]
Description=Silver Sentinel
After=network.target

[Service]
User=sentinel
WorkingDirectory=/opt/silver-sentinel
Environment=SILVER_DATA_DIR=/var/lib/silver-sentinel
Environment=SILVER_AUTOSTART_MONITOR=1
ExecStart=/opt/silver-sentinel/.venv/bin/silver-sentinel serve --host 127.0.0.1 --port 8000
Restart=always
RestartSec=5
NoNewPrivileges=true
PrivateTmp=true

[Install]
WantedBy=multi-user.target
```

### Docker

```bash
cp .env.example .env
docker compose up -d
```

`SILVER_AUTOSTART_MONITOR=1` 会让内置调度器随进程启动（单进程内线程，不需要 Redis/Celery）。

### 反向代理

控制台**不带鉴权**，设计上只监听 `127.0.0.1`。对外提供服务时必须加一层：

```nginx
location / {
    auth_basic "sentinel";
    auth_basic_user_file /etc/nginx/.htpasswd;
    proxy_pass http://127.0.0.1:8000;
}
```

## 五、容量与性能

单个线索的完整扫描约 **0.1–0.4 秒**（离线）或 **2–6 秒**（联网查 RDAP/CT）。

| 数据量 | SQLite 表现 | 建议 |
| --- | --- | --- |
| < 1 万条线索 | 无感知 | 单机 SQLite |
| 1–10 万 | 列表查询 < 200ms | 加索引（已内置），定期 `VACUUM` |
| > 10 万 | 写入开始排队 | 切 Postgres |

APK 解析限制：单文件 ≤ 150MB，内部扫描 ≤ 80MB，单条目 ≤ 24MB。超过则跳过该条目而非失败。

## 六、扩展点

### 加一个情报源

```python
# collectors/mysource.py
from .http import client

def lookup(host: str) -> dict | None:
    data = client.get_json(f"https://example.org/api/{host}")
    return {"listed": bool(data and data.get("bad"))}
```

在 `intake._collect_url_facts` 里调用并写入 `facts`，再到 `builtin.yaml` 加一条 `REP-xxx` 规则。

### 加一个举报渠道

在 `respond.CHANNELS` 加一项，`render_markdown` 会自动套用统一结构。若字段差异大，覆写 `payload`。

### 换 LLM

只要兼容 OpenAI `/chat/completions` 即可（DeepSeek、通义、Moonshot、vLLM、Ollama）：

```bash
SILVER_LLM_BASE_URL=http://localhost:11434/v1
SILVER_LLM_API_KEY=ollama
SILVER_LLM_MODEL=qwen2.5:14b
```

## 七、安全与合规

| 风险 | 处置 |
| --- | --- |
| 凭据泄露 | 只从环境变量读；`.env` 在 `.gitignore`；日志不打印 header |
| 出站暴露采集机 | `opsec` 四道闸：分类 / 代理 / 指纹 / 脱敏；可疑目标默认 fail-closed |
| 沙箱泄露内网与真实 IP | 无隔离出口拒绝运行；禁非代理 UDP；屏蔽 WebRTC；只发 GET/HEAD |
| 举报材料含自身基础设施 | 导出前 `assert_clean`，检出自身 IP/主机名/数据目录即中止 |
| 举报材料含个人信息 | 生成前对手机号/身份证/银行卡做掩码（`llm.redact`） |
| 送 LLM 的数据 | 先脱敏再发送；可完全关闭（`SILVER_LLM_ENABLED=0`） |
| 证据被篡改 | 哈希链 + `verify-chain` 命令 |
| 控制台暴露公网 | 默认仅监听 127.0.0.1，前置 Basic Auth |
| 法律定性风险 | 报告固定包含「线索而非定性结论」声明 |

**数据保留建议**：涉诈样本（APK）本身可能包含恶意代码，只做静态分析、不执行、不双击。归档 6–12 个月后如已结案可清理。

## 八、日常运维清单

| 频率 | 动作 |
| --- | --- |
| 每日 | 看「待处置」数量；处理 `high_risk` 以上新线索 |
| 每周 | `silver-sentinel verify-chain` 校验证据链；检查调度记录有无连续失败 |
| 每月 | 更新 `official_watchlist.yaml`；复核误报（把 `benign` 的样本回灌规则） |
| 每季 | 校准阈值；清理低价值监控目标；备份演练 |

### 怎么发现自己在误报

控制台「线索库 → 全部判定 → 已排除」，如果同一类特征反复被人工判为 `benign`，说明某条规则权重过高或词表过宽。调低 `weight` 或收窄 `text_any`，然后跑测试确认没有回归。

### 日志

```bash
journalctl -u silver-sentinel -f
```

关键日志：`聚类完成`、`监控任务失败`、`安装包入库失败`。采集失败默认只记 debug，不影响主流程 —— 这是刻意的：情报源不稳定是常态，不能让它拖垮研判。

# v1.0 增补：从「查线索」到「长期盯着」

v0.1 是同步工具：给它一个对象，它还你一个判定。
v1.0 是常驻系统：三路发现源持续喂入，研判/富化/建图/归因按周期跑，证据只追加，副本往外推。

## 九、发现层

### 9.1 三路冗余

| 通路 | 实现 | 频率 | 依赖 |
| --- | --- | --- | --- |
| CT 日志直连 | `discover/ct.py::CTLogFollower`，按 RFC 6962 拉 `get-sth` / `get-entries` | `SILVER_CT_POLL_INTERVAL`（默认 60s） | 出网 HTTPS |
| certstream | `CertStreamClient`，WebSocket 订阅聚合流 | 实时 | `websockets`（可选） |
| 域名排列 | `discover/dnsprobe.py`，词根派生 + 批量解析 | 常驻循环 | DNS（`dnspython`） |

游标存 `data/ct_state/<log>.json`，重启从上次位置续跑；落后太多（`max_lag`）时跳段，不让一次宕机把进程卡在历史数据里。

```bash
silver-sentinel discover status
```

看三件事：`followers[].index/tree_size` 是否在前进、`stream.connected`、`dns.pool` 里有几个解析器是活的。

### 9.2 准入与降噪

发现层故意宽：**命中一个词根就入库**。噪音靠后面三道闸拦：

1. 白名单（极窄，且防伪造后缀）
2. 语义簇降权（无强簇支撑时 `policy_theme`/`carrier`/`inducement` 打到 0.30–0.55）
3. ICP 备案（只查 `candidate` 以上，令牌桶 + 长缓存，未知不等于未备案）

### 9.3 容量规划

| 参数 | 默认 | 调大的后果 |
| --- | --- | --- |
| `SILVER_CT_POLL_BATCH` | 256 | 单轮抓更多，CPU 峰值更高 |
| `SILVER_DISCOVER_QUEUE` | 50000 | 更抗突发，内存占用上升 |
| `SILVER_WORKERS` | 8 | 研判更快，但对外请求更密 |

CT 日志每天新增百万级证书，一条日志的 `tree_size` 增速可以当吞吐基线。实测单核在纯匹配环节能到 5 万域名/秒，瓶颈在 HTTP 拉取与解析，不在匹配。多日志并行 + 每轮批量的组合，比加机器有效。

## 十、图谱与归因

```
Asset ──HOSTED_ON──▶ Domain ──RESOLVES_TO──▶ IP
  │                    │
  ├──SIGNED_WITH──▶ Cert ◀──SHARES_CERT── APK
  ├──USES_WALLET──▶ Wallet
  ├──SAME_TEMPLATE──▶ Template
  └──ICP_ENTITY──▶ Entity ◀──ICP_ENTITY── Domain
```

- 节点 20 类、关系 17 种，权重见 `graph/schema.py::RELATION_WEIGHTS`。
- 后端二选一：内置 SQLite 图引擎（零依赖，BFS 逐层 `IN` 查询）或 Neo4j（Cypher）。`get_graph()` 自动选择，Neo4j 连不上自动回落并记 warning。
- 社区发现：节点 ≤50 走连通分量，否则 Louvain；只对「含 ≥2 个可疑资产或有已确认资产」的社区建团伙。

```bash
silver-sentinel graph rebuild      # 重建 + 重新归并
silver-sentinel graph stats
```

## 十一、证据可靠性

| 层 | 机制 | 校验方式 |
| --- | --- | --- |
| 事件日志 | 只追加；`seq`+`prev_hash`+内容哈希；group commit fsync；`flock` 跨进程 | `silver-sentinel log verify` |
| 证据文件 | sha256 内容寻址 | 落盘与读取时各校验一次 |
| 副本 | 增量分片 + 回读比对大小 | `replica sync` 返回值里的 `verified` |
| 数据库 | `sqlite3.backup` 一致性快照 | 可 `sqlite3 integrity_check` |
| 加密证据仓 | AES-256-GCM；账本 + 保管链双链；内容寻址 | `silver-sentinel vault verify` |
| 多端账本 | 每节点独立链，按 sha256 合并 | `vault verify` 会逐个节点报告 head 与断点 |

故障演练：

```bash
# 删掉中间一行，看能不能发现
sed -i '500d' data/events.jsonl && silver-sentinel log verify
# 期望：异常：第 500 行，序号断裂：期望 500 实际 501

# 从副本恢复
silver-sentinel replica restore
```

**证据仓与副本的分工**：副本保证"机器没了能起来"，证据仓保证"证据本身可验证、可携带、可合并"。
原始文件加密后放 `data/vault/blobs`（或 S3/WebDAV/IPFS），仓库侧只导出账本与保管链。
新节点只需同一把密钥 + 同一后端，`vault pull` 即可重建全部历史。详见
[证据保管与多端同步](09-证据保管与多端同步.md)。

## 十二、部署编排

| 场景 | 命令 | 说明 |
| --- | --- | --- |
| 单机最小 | `docker compose up -d --build` | 一个容器包揽发现+调度+控制台 |
| 要图谱库 | `--profile graph` | Neo4j 5 community，仅暴露 7474 到本机 |
| 要异地副本 | `--profile replica` | MinIO + 自动建桶 |
| 要 APK 动态分析 | `--profile sandbox` | MobSF，端口 8001 |
| 要真实网页取证 | 构建时 `WITH_SANDBOX=1` | 镜像 +400MB，装 chromium |

容器是只读根文件系统（`read_only: true`），只有数据卷和 `/tmp`、`~/.cache`（沙箱用）可写。`no-new-privileges` 全程开启。

生产建议：

1. 反代上 Basic Auth 或 OAuth2 Proxy，控制台不直接对公网。
2. 数据卷单独挂盘，`SILVER_REPLICA_TARGET` 指到另一台机器或对象存储。
3. 系统级 `systemd` 或 compose `restart: unless-stopped`，进程内已做三级降级，单点外部依赖挂掉不会导致退出。
4. 日志走 `json-file` 限流（20MB × 5），或改 `SILVER_LOG_JSON=1` 交给 Loki。

## 十三、运维指标

```
GET /api/metrics        # Prometheus 文本
GET /api/stream         # SSE：discovery / cycle / asset 事件
GET /api/ops/status     # 能力降级 + 任务记账 + 积压
```

| 指标 | 含义 | 报警建议 |
| --- | --- | --- |
| `sentinel_assets_total{tier}` | 各档位资产数 | `confirmed` 突增需人工确认 |
| `sentinel_discover_certs_total` | 已处理证书数 | 10 分钟不涨 → CT 通路断 |
| `sentinel_discover_queue` | 待落库队列 | > 容量 50% 持续 5 分钟 |
| `sentinel_eventlog_ok` | 证据链完整性 | 0 → 立即人工介入 |
| `sentinel_cycle_errors_total` | 周期错误累计 | 速率 > 0 持续 15 分钟 |
| `sentinel_replica_lag_seconds` | 副本延迟 | > 3× 间隔 |

「能力降级」不是故障：ICP 没配、MobSF 没起、Neo4j 没装，系统照跑，运维页如实标 `off`/`static-only`。真正需要报警的是「昨天还在跑，今天不跑了」。
