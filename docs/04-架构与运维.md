# 架构、部署与长期运维

---

## 一、数据流

```
                        ┌──────────────┐
   链接 / 域名 / APK ──▶ │  normalize   │  URL 去追踪参数、域名取可注册域、指标抽取
   文本 / 小程序名       └──────┬───────┘
                                ▼
                        ┌──────────────┐
                        │  collectors  │  只读被动情报，不访问目标站点
                        └──────┬───────┘
              ┌─────────────────┼─────────────────┐
              ▼                 ▼                 ▼
        crt.sh / RDAP     URLhaus / OpenPhish   APK 静态解析
        DNS 变体探测      官方通报清单匹配       AXML/权限/证书/模板指纹
              └─────────────────┼─────────────────┘
                                ▼
                        ┌──────────────┐
                        │    scoring   │  声明式规则求值 → noisy-OR 聚合 → 弃权判定
                        └──────┬───────┘
                                ▼
                        ┌──────────────┐
                        │  analyzers   │  LLM 叙事（可弃权） / Union-Find 团伙归并
                        └──────┬───────┘
                                ▼
        ┌───────────────────────┼───────────────────────┐
        ▼                       ▼                       ▼
   assets/signals           evidence                campaigns
   （线索与依据）           （哈希链）              （团伙聚合）
                                ▼
                        ┌──────────────┐
                        │   respond    │  举报材料 / 一页纸
                        └──────────────┘
```

每次扫描都是幂等的：同一对象重复扫描只累加 `scan_count`，信号整体重写，不会堆积重复行。

## 二、模块职责

| 模块 | 职责 | 关键约束 |
| --- | --- | --- |
| `config.py` | 环境变量与 `.env` | 敏感值只从环境读，不进日志 |
| `normalize.py` | 规范化与指标抽取 | 零宽字符清除、URL 去参、Luhn 校验 |
| `models.py` | SQLAlchemy 2.0 模型 | 资产 `(kind, normalized)` 唯一 |
| `db.py` | 会话、WAL、证据链校验 | SQLite 开 `foreign_keys`、`busy_timeout` |
| `scoring/engine.py` | 规则求值 + 聚合 | 单条规则异常不中断整次研判 |
| `collectors/apk.py` | APK 静态分析 | 自实现 AXML 解析，失败降级正则 |
| `analyzers/llm.py` | LLM 研判 | 严格 JSON 校验 + 脱敏 + 弃权 |
| `analyzers/cluster.py` | 团伙归并 | Union-Find，结果幂等 |
| `intake.py` | 扫描编排 | 采集失败不影响规则判定 |
| `respond.py` | 举报材料 | 只陈述事实，不做法律定性 |
| `monitor.py` | 调度 | 数据库存 `next_run_at`，多实例安全 |
| `api.py` / `web/` | 控制台 | 无构建步骤，零 node 依赖 |

## 三、存储

默认单文件 SQLite（WAL 模式）。

| 项 | 位置 | 说明 |
| --- | --- | --- |
| 数据库 | `data/sentinel.db` | 线索、信号、证据元数据、举报草稿 |
| 证据文件 | `data/evidence/<sha256>.<ext>` | 内容寻址，天然去重 |
| 官方清单 | `data/official_watchlist.yaml` | 可选覆盖，缺省用包内置版本 |

**备份**：只需备份 `data/` 整个目录。

```bash
sqlite3 data/sentinel.db ".backup 'data/backup-$(date +%F).db'"
tar czf evidence-$(date +%F).tar.gz data/evidence
```

**切 Postgres**（线索量 > 10 万或需要多人并发时）：

```bash
pip install "psycopg[binary]"
SILVER_DB_URL=postgresql+psycopg://user:pass@host/sentinel silver-sentinel serve
```

表结构由 SQLAlchemy 自动创建，无需迁移脚本。

## 四、部署

### 单机（推荐起步）

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -e .
silver-sentinel serve --host 127.0.0.1 --port 8000
```

systemd 单元：

```ini
[Unit]
Description=Silver Sentinel
After=network.target

[Service]
User=sentinel
WorkingDirectory=/opt/silver-sentinel
Environment=SILVER_DATA_DIR=/var/lib/silver-sentinel
Environment=SILVER_AUTOSTART_MONITOR=1
ExecStart=/opt/silver-sentinel/.venv/bin/silver-sentinel serve --host 127.0.0.1 --port 8000
Restart=always
RestartSec=5
NoNewPrivileges=true
PrivateTmp=true

[Install]
WantedBy=multi-user.target
```

### Docker

```bash
cp .env.example .env
docker compose up -d
```

`SILVER_AUTOSTART_MONITOR=1` 会让内置调度器随进程启动（单进程内线程，不需要 Redis/Celery）。

### 反向代理

控制台**不带鉴权**，设计上只监听 `127.0.0.1`。对外提供服务时必须加一层：

```nginx
location / {
    auth_basic "sentinel";
    auth_basic_user_file /etc/nginx/.htpasswd;
    proxy_pass http://127.0.0.1:8000;
}
```

## 五、容量与性能

单个线索的完整扫描约 **0.1–0.4 秒**（离线）或 **2–6 秒**（联网查 RDAP/CT）。

| 数据量 | SQLite 表现 | 建议 |
| --- | --- | --- |
| < 1 万条线索 | 无感知 | 单机 SQLite |
| 1–10 万 | 列表查询 < 200ms | 加索引（已内置），定期 `VACUUM` |
| > 10 万 | 写入开始排队 | 切 Postgres |

APK 解析限制：单文件 ≤ 150MB，内部扫描 ≤ 80MB，单条目 ≤ 24MB。超过则跳过该条目而非失败。

## 六、扩展点

### 加一个情报源

```python
# collectors/mysource.py
from .http import client

def lookup(host: str) -> dict | None:
    data = client.get_json(f"https://example.org/api/{host}")
    return {"listed": bool(data and data.get("bad"))}
```

在 `intake._collect_url_facts` 里调用并写入 `facts`，再到 `builtin.yaml` 加一条 `REP-xxx` 规则。

### 加一个举报渠道

在 `respond.CHANNELS` 加一项，`render_markdown` 会自动套用统一结构。若字段差异大，覆写 `payload`。

### 换 LLM

只要兼容 OpenAI `/chat/completions` 即可（DeepSeek、通义、Moonshot、vLLM、Ollama）：

```bash
SILVER_LLM_BASE_URL=http://localhost:11434/v1
SILVER_LLM_API_KEY=ollama
SILVER_LLM_MODEL=qwen2.5:14b
```

## 七、安全与合规

| 风险 | 处置 |
| --- | --- |
| 凭据泄露 | 只从环境变量读；`.env` 在 `.gitignore`；日志不打印 header |
| 举报材料含个人信息 | 生成前对手机号/身份证/银行卡做掩码（`llm.redact`） |
| 送 LLM 的数据 | 先脱敏再发送；可完全关闭（`SILVER_LLM_ENABLED=0`） |
| 证据被篡改 | 哈希链 + `verify-chain` 命令 |
| 控制台暴露公网 | 默认仅监听 127.0.0.1，前置 Basic Auth |
| 法律定性风险 | 报告固定包含「线索而非定性结论」声明 |

**数据保留建议**：涉诈样本（APK）本身可能包含恶意代码，只做静态分析、不执行、不双击。归档 6–12 个月后如已结案可清理。

## 八、日常运维清单

| 频率 | 动作 |
| --- | --- |
| 每日 | 看「待处置」数量；处理 `high_risk` 以上新线索 |
| 每周 | `silver-sentinel verify-chain` 校验证据链；检查调度记录有无连续失败 |
| 每月 | 更新 `official_watchlist.yaml`；复核误报（把 `benign` 的样本回灌规则） |
| 每季 | 校准阈值；清理低价值监控目标；备份演练 |

### 怎么发现自己在误报

控制台「线索库 → 全部判定 → 已排除」，如果同一类特征反复被人工判为 `benign`，说明某条规则权重过高或词表过宽。调低 `weight` 或收窄 `text_any`，然后跑测试确认没有回归。

### 日志

```bash
journalctl -u silver-sentinel -f
```

关键日志：`聚类完成`、`监控任务失败`、`安装包入库失败`。采集失败默认只记 debug，不影响主流程 —— 这是刻意的：情报源不稳定是常态，不能让它拖垮研判。
