日期：2026-11-21

| 版本 | 判断的根因 | 修复 | 结果 |
|---|---|---|---|
| v1.16.9（历史） | 浏览器进程泄漏 | PID 进程树强杀 | 修好了当时的问题 |
| v1.16.11 | 失败站超时误分 transient，10 分钟重试拉 Chromium | STALL 长冷却 + 超时 90s + 截图限时 | 部署后仍卡死 |

## 决定性证据：py-spy 抓取 100% CPU 线程堆栈

部署 v1.16.12 后，进程 RSS 1.2G、单线程 CPU 98.8%、持 GIL（`active+gil`）。
装 py-spy 抓堆栈，真凶是 `vault-sync` 线程：

```
Vault.read_manifest (vault.py:589)   ← json.loads 正在解析
Vault._last_entry (vault.py:602)
Vault._append_custody (vault.py:617)
Vault.push (vault.py:724)
Vault.sync_once (vault.py:1162)
Vault._loop (vault.py:1186)
```

`read_manifest` 用 `path.read_bytes().splitlines()` **把整个 JSONL 账本载入内存再逐行解析**。
生产 `custody-node-375a52dc.jsonl` 已涨到 **94.6MB / 21.7 万行**。`_last_entry()` 只想要最后一行，
却每次全量解析 94MB——每 120 秒同步一轮，每轮多次调用。

实测（生产真实文件）：

| 实现 | 耗时 | 内存 |
|---|---|---|
| 旧 `read_manifest`（全量） | **2.32s** | 94MB bytes + 21.7 万行列表 + 同量级 dict，峰值几百 MB |
| 新 `_last_entry`（只读末尾） | **0.0006s** | O(1)，几 KB |

**加速 3991 倍**。

## 为什么这导致了「卡死」

1. vault-sync 每 120s 全量解析 94MB → 100% CPU、几百 MB 内存尖峰，**持有 GIL 几十秒**（单线程 Python，GIL 被霸占）；
2. GIL 被霸占 → API 请求、取证线程、监控全部排队等 GIL → ping 从 0.01s 恶化到 2~26s；
3. 内存尖峰 + 其他线程 → 可用内存跌到 57~188MB → 触发前面分析的 swap 颠簸、取证线程卡 D 状态；
4. 账本还在持续增长（append-only），解析越来越慢——正反馈。

前面的 v1.16.11/v1.16.12 修的都是「下游症状」（失败重试、swap、内存看门狗），
真正的「上游病灶」是这个每 120 秒发作一次的账本全量解析。

## 修复（v1.16.13）

| # | 位置 | 改动 |
|---|---|---|
| 1 | `vault.py` `iter_manifest()` | 新增流式逐行解析生成器，绝不整表载入。 |
| 2 | `vault.py` `read_manifest()` | 改为 `list(iter_manifest())`，保留语义但供非热路径使用。 |
| 3 | `vault.py` `_last_entry()` | **反向读取文件末尾最后一个完整行**（O(1)），尾部损坏时兜底全表扫描。这是每轮 push 的热路径。 |
| 4 | `vault.py` `push()` | 已固化证据的 sha256 集合改用 `iter_manifest()` 流式提取，消除全表列表构造。 |

## 残余与边界

- 仍有极少量取证超时（约 1 次/10 分钟，多为个别卡死站），现已归 STALL 冷却 48h，且超时会主动关浏览器释放内存——内存尖峰后能自愈回落，不再累积。
- 取证吞吐仍偏低：1.9G 内存下可用内存常在 350MB 阈值附近波动，看门狗会周期性暂停取证保 API。这是硬件瓶颈，代码已做到「卡不死、能自愈」，彻底提升吞吐仍需扩容内存或迁移。
- 生产保留：`SILVER_WORKERS=3`、`SILVER_CAPTURE_MIN_FREE_MEM_MB=350`、`vm.swappiness=10`、`vm.dirty_ratio` 默认。

## 经验教训

- **先抓堆栈再改代码**：前两版靠「症状推理」修下游，第三次用 py-spy 拿到 `read_manifest` 的实际堆栈才锁病灶。
- **append-only 文件永远不要全量 `read_bytes().splitlines()`**：取末行就反向读，取存在性就流式扫，取计数就逐行加。
- **GIL 是隐藏放大器**：一个 CPU 密集线程能拖慢整个进程的所有线程，表现为「网页卡死」而非「某后台任务慢」。
