# 取证强度动态调配（v1.16.16）

日期：2026-11-27

## 需求

无头浏览器是内存占用大头。要在本机限定：不要无限制并行取证，按性能实时调配
取证任务；若界面不能手动设置则加入该逻辑；以「不用/少量 swap」为内存标准。

## 现状诊断

| 事实 | 数据 |
| --- | --- |
| 取证线程 | 已是单线程池 `max_workers=1`、`run_batch(limit=1)`，不存在真正并行 |
| 旧判定 | `memory_ok()` 只看 `MemAvailable >= 固定阈值 350MB`（env 未设，走默认） |
| 新机内存 | 总 1.9G，sentinel 进程 RSS 925MB，可用长期 240~280MB |
| 后果 | 每轮可用内存都够不到 350MB → 取证几乎全被拦，周期空转；近 1 小时仅 3 条成功 |
| swap | 已用 1.5G，但旧逻辑完全不检测 |

根因：用一个**脱节的固定数字**当门槛，既没看 swap，也没按性能调配。可用内存
永远差一点，于是「过度保守 + 完全停摆」同时发生。

## 修复（v1.16.16）

### 1. 新标准：以 swap 为主轴（`capture.py`）

新增 `capture_budget()`，每轮采样三项实时指标：
- `MemAvailable`（`/proc/meminfo`）
- `SwapUsed`（SwapTotal − SwapFree）
- `swapin` 速率（`/proc/vmstat` pswpin 每秒增量，>1024 页/s 判为内存颠簸）

动态给出本轮取证条数：

| 条件 | 条数 |
| --- | --- |
| swap 已用 ≥ 上限，或可用内存 < 下限，或正在剧烈换入 | **0**（停一轮） |
| swap 空闲（≤ 上限 25%）且内存宽裕（≥ 下限 2 倍） | **max_batch**（默认 2） |
| 其余 | **1** |

带**滞回**：一旦暂停，swap 要降到上限的 80% 以下才恢复，避免阈值边缘反复横跳。

### 2. worker 接线（`worker.py`）

`CaptureWorker.tick()` 不再用固定 `memory_ok()`，改为 `budget = capture_budget()`，
按 `budget.slots` 决定 `run_batch(limit=...)`。暂停轮把原因、可用内存、swap 写入
体征与日志，任务留队列，压力缓解后自动恢复。`self.last` 增加 budget/avail/swap 字段。

### 3. 界面可手动设置（`runtime_settings` / `api_extra` / HTML / JS）

设置页新增「取证强度」区块，4 个参数（存 SQLite，改完即时生效，TTL 5s）：

| 参数 | 键 | 默认 | 含义 |
| --- | --- | --- | --- |
| 动态调配 | `capture.adaptive` | 开 | 关则退回旧的固定单条逻辑 |
| 每轮最多 | `capture.max_batch` | 2 | 内存宽裕、swap 空闲时的条数（1~4） |
| swap 上限 | `capture.swap_limit_mb` | 256 | 已用超过即降速/暂停，0=不限制 |
| 内存下限 | `capture.min_free_mem_mb` | 120 | 可用低于此值完全暂停 |

API：`POST /api/settings/capture` 扩展上述字段；`GET /api/settings` 回显。

## 运维建议（新机 1.9G）

- 保持动态调配开启；每轮最多 2 条起步，观察 swap 不再增长再酌情上调。
- swap 上限 256MB：当前已用 1.5G 属历史换出，需先重启进程让 swap 回落，
  再让新策略接管；否则策略会因 swap 超上限持续暂停（这是符合"少用 swap"标准的）。
- 手动兜底：把 `capture.adaptive` 关掉即回到每轮 1 条的旧行为。
