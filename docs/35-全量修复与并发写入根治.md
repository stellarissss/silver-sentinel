## 1. 这轮做了什么

主目标不是"让某个报错消失"，而是把**根因**修掉：取证写库为什么每小时撞几十次

## 2. 证据链：一处历史断裂 + 一个一直没被发现的算法错误

### 断裂不是篡改，是并发写入

全库 3.8 万条证据，链只在 `id=15535` 断了一处。断点是 `aq9d84.cn` 那批取证被
`yy-tv-baidu.com` 那批插到中间：前者按旧链尾算好了 `prev_hash`，后者先提交占了
中间 5 个 id。两个事务各读各的链尾，提交顺序和构造顺序对不上，链就分叉了。
15535 之后两万多条全部连续——取证后来改成单工作线程，并发只留了这一处旧账。

**没有重算整条链**。改两万多条历史哈希，正好破坏"链不可篡改"这件事本身。做法是
新增 `chain_anchors` 表，把 15535 登记成受控断点：`verify_chain()` 从这里另起一段，
历史哈希原样保留，断点可查可审计。健康检查不再把并发写入误报成"证据被改动"。

配套命令：

```
silver-sentinel chain verify          # 校验 + 列出锚点
silver-sentinel chain list
silver-sentinel chain add 15535 --reason "并发写入导致的已知分叉" --by ops
```

### `verify_chain(asset_id)` 以前必然误报

链是全局的：一条证据的 `prev_hash` 指向**全库上一条**的 `chain_hash`，那条可能属于
另一个资产。按资产过滤时旧代码还从 `prev=""` 起算，于是只要这个资产不是全库第一条，
第一条证据的 `prev_hash` 就一定不等于空串，立刻返回"链哈希不匹配"。
`GET /api/verify-chain?asset_id=N` 这个参数等于完全不能用。

现在先建 `id → 全库前一条链尾` 的映射，按资产过滤时用它做期望值；两种模式共用一套逻辑。

### 写链改串行

`chain_tip()` 读链尾、算 `prev_hash`、`flush` 落行，这三步中间只要插进另一个写事务就分叉。
新增 `chain_write_scope()`：用 `fcntl.flock` 做跨进程排他锁，包住**整个**事务（不是只在
`append()` 内部锁——事务提交发生在 `with` 退出时，锁太短没用）。所有写 evidence 的入口
（capture、intake、APK 失败留痕）都改走它。同进程嵌套用线程内深度计数放行，避免两个
fd 各抢一把 `LOCK_EX` 互相顶死。

## 3. `database is locked`：根因是隐式 autoflush

日志里的报错都带 `Query-invoked autoflush`：WAL 下一个事务里的 SELECT 会先触发隐式
flush 去抢写锁，另一个连接正持锁时就撞上。`session_scope` 以前用 SQLAlchemy 默认的
`autoflush=True`，而 capture 里那个 340 行事务塞满了各种查询（链尾查重、用途补算、
重评读正文），每一次都是一次抢锁机会。

改成 `autoflush=False`，需要提前落行的地方全部显式 `flush()`。这一改暴露了一处真
缺陷：`run_batch()` 回收 stale 任务后，靠隐式 flush 让下一条 `SELECT state='queued'`
看见新状态；补上显式 `s.flush()` 后测试恢复通过——不是改测试迁就实现，是补回了本来
就该写的那行。

另外 `run_chain_write(fn)` 提供撞锁时的整体重试，用回调而不是 `@contextmanager`
（生成器 yield 之后重试会二次 yield，直接抛 `RuntimeError`）。

## 4. 判定一致性：20 分的站不该挂 high_risk

白名单把分数压到 20，但旧代码 `_apply_claim()` 无条件给过 `high_risk`，verdict 没跟着
回退；资产随后沉进 cold/dismissed，再也不进周期重评，误报就永久留在高危池。
上一轮审批清零后第二天又长出 19 条，就是这么来的。

三层一起修：

- `aggregate()` 后加 `normalize_verdict()`：机器判定不能比分数应得的更重。硬证据提级
  （伪造政府标识码 95 分）、人工终审 `confirmed` 一律豁免——否则会把上一轮确认的
  89 条仿冒财政部站群误降成 `insufficient`。
- `pending_assets()` 用 `or_` 把"判定比分数重"的冷存档资产拉回周期研判，自动纠正。
- 新增 `reconcile-verdicts`（默认 dry-run，`--apply` 才写），一次性修存量，逐条留痕。

## 7. 已知限制

- capture 那个 340 行事务**没有拆分**。本轮用"串行化 + 关 autoflush + 重试工具"消掉了
  并发分叉和隐式抢锁两个根因，但把一个长事务重构成短事务属于另一量级的改动，另开一轮做。
- `chain_anchors` 是运维登记，不是自动发现。新出现并发分叉仍会先报 `ok:false`，由人确认
  是"并发"还是"真被改"之后再登记——这个判断不该交给机器。
- 同盘副本的旧冗余文件需要单独清理（代码只保证不再新增），本轮部署后单独处理。

## 8. 补记：判定阈值口径统一（部署后只读复查发现）

v1.16.6 主体部署后，只读复查生产发现仍有 21 条 `high_risk`，其中
`djzb-douyin.cc` 36.4 分、`mkt.bypeople.com.br` 38.8 分。按上一轮体检报告里
"代码默认 40" 的口径它们是误报，但生产 `get_ruleset().thresholds` 实际是
`{'suspicious': 15.0, 'high_risk': 35.0, 'confirmed': 70.0}` —— 规则文件
`rules/builtin.yaml` 写的就是 35，36~39 分挂 `high_risk` 按现行规则**合法**。
`reconcile-verdicts` dry-run 因此只报 31 条低分残留（8.4~11.1 分），
`high_risk` 待降级 0 条。上一轮报告按 40 判断的部分需要据此更正。

真正的问题是**同一套规则有两个默认值**：加载成功按 35，YAML 一旦缺字段
回退到代码里的 40；`priority_of()` 还硬编码 40 做 P2 分界，于是 35~39 分的
高危资产被排到 P3，人工审阅顺序被颠倒。`cli.py`、`pipeline.py` 也各自写了
`40`/`15` 兜底。

修法是收成单一常量 `DEFAULT_THRESHOLDS`（必须与 YAML 相等，由测试钉死）：

- `RuleSet.thresholds` 默认工厂、`load_ruleset()` 回退全部引用它；YAML 缺字段
  时按常量逐键补齐，不再整体换成另一套字典。
- `aggregate()` / `verdict_for_score()` / `normalize_verdict()` /
  `cmd_reconcile_verdicts()` / `pending_assets()` 的 `.get` 兜底统一引用常量。
- `priority_of()` 的 P1/P2/P3 分界改从常量取，与判定档一致。
- 新增 `tests/test_threshold_consistency.py`：代码默认 == YAML、缺字段补齐、
  兜底来自单一常量、分档联动、源码无硬编码兜底残留。

**口径结论**：35 分是现行规则，不是 bug。若要压低非涉老目标（体育站、含
"people" 的巴西域名等）进高危池，属于**规则/门槛调整**，与本轮一致性修复
是两件事，需单独评估；不要靠改代码兜底"悄悄"抬门槛。

## 9. 补记二：同盘副本整轮跳过 + 磁盘清理（部署后只读复查发现）

第 5 节的副本修复只挡住了 vault 密文与 DB 快照。部署后只读复查发现
`replica/events`、`replica/evidence` 仍在写：`replica_state.history` 里每轮都有
`event_bytes=28682/10907`、`evidence_files=65/38`，实测最近一小时新增
**377 个** evidence 副本文件。只跳过两类是同类根因的遗漏——同盘「副本」
本来就不是备份，四类同步都不该跑。

修法：`run_once()` 在同盘 dir 后端整轮短路（`skipped=True` + 保留 warning），
四个同步函数各自也加同盘防御，避免被 CLI 单独调用时绕过。新增
`tests/test_replica_same_device.py`（整轮跳过、单点防守、异盘恢复同步）。
