# 控制台重构与访问控制（v1.4）

v1.3 之前，控制台是「能看懂数据」的水平：信息摆得全，但读起来累，也没法给外面的人看——它默认只监听回环地址，且没有任何登录。v1.4 把这两件事一起解决：界面按现代极简线条风重做，同时补上访问口令与一键部署。

## 一、界面为什么重做

旧界面的问题不是丑，是**层级不清**：卡片阴影、圆角、渐变、彩色标签同时争夺注意力，用户不知道先看哪。研判是慢思考工作，屏幕上不该有十个东西同时喊「看我」。

新风格只用三样东西表达结构：**纸底、细线、墨色阶**。唯一的彩色是朱红，且只给「需要立刻处理」的东西。

### 设计令牌

全部定义在 `web/static/style.css` 顶部的 `:root`，换肤只改这一处：

| 令牌 | 作用 |
| --- | --- |
| `--paper` / `--surface` | 页面底色与卡片底色，两者差一级明度，不靠阴影分层 |
| `--rule` / `--rule-2` | 1px 分隔线。所有区域边界靠它，不用 border-radius 堆容器 |
| `--ink` / `--ink-2` / `--ink-3` / `--ink-4` | 四级墨色，从正文到辅助信息到占位文字 |
| `--accent` | 单一朱红，只用于高危、当前选中、需要行动的按钮 |

规则：**零阴影、零渐变、最大圆角 2px**。深浅两套主题共用同一组语义变量，`body[data-theme="dark"]` 只覆写数值。

### 结构调整

- **九视图**：概览 / 发现流 / 研判台 / 线索库 / 关系图谱 / 团伙 / 监控 / 运维 / 规则库。左侧导航只留线条图标 + 中文标签，移动端折叠成图标条。
- **研判台两栏**：左侧输入与操作，右侧 `scan-recent` 常驻最近一次结果。之前是单列，填完表单要往下滚很久才看到结果。
- **KPI 数字**：从 0 收敛到目标值（`ui.js` 的 `countUp`），时长 600ms。不是为了炫技——数字跳变能让用户确认「这是新数据」，静止的数字看不出来。
- **条形图**：宽度由 `data-w` 驱动，在 `requestAnimationFrame` 里起跳，取代原来的直接写死宽度。
- **表格**：表头可点击排序，`.table-wrap > table` 兜底选择器保证历史渲染路径缺 class 时样式不塌。
- **实时流**：`grid-template-areas` 重排成「时间 / 标签 / 域名 / 得分」四列，窄屏下域名与命中词换行，不再挤成一坨。
- **图谱**：节点改成空心圆环，用纸色填充盖住穿过的边，视觉上边「从节点后面走」；边用 `withAlpha(ink, .15)`，主题切换时监听 `ss:theme` 重绘。
- **命令面板**：`⌘K` / `Ctrl+K` 唤出，支持中文别名搜索（输入「研判」「图谱」「规则」直接跳），`Esc` 关闭。
- **顶部进度线**：`#topline` 在每次请求期间做不确定态动画，替代原来只有按钮转圈。
- **主题持久化**：写入 `localStorage` 的 `ss-theme`，首屏用内联脚本读取，避免闪白。

### 性能取舍

没有引入前端框架，仍是原生 DOM + 一个 200 行的 `ui.js`。整个静态资源（含 CSS）gzip 后不到 40KB，首屏在 2G 网络下也能开。代价是视图切换要手写显隐，收益是部署时不依赖 node 构建链——`pip install` 完就能跑。

## 二、访问控制

### 模型

```
浏览器 ──(口令)──> /auth/login ──> Set-Cookie: ss_session=<HMAC 签名>
                                        │
                       ┌────────────────┴────────────────┐
                   cookie 有效                      无 cookie / 过期
                       │                                 │
                  放行 /api/*                     /api/* → 401
                                                 /      → 302 /login
```

- **会话**：`HMAC-SHA256(secret, exp)`，secret 由口令派生。改口令 → 旧会话全部失效（这是有意的，口令泄露时能一次性踢掉所有人）。
- **TTL**：默认 12 小时，`SESSION_TTL` 可调。
- **三种携带方式**：`ss_session` cookie（浏览器）、`Authorization: Bearer <口令或 session>`（脚本）、`/api/*?token=<口令>`（下载链接，比如证据包）。
- **公开路径**：`/login`、`/auth/login`、`/auth/logout`、`/static/*`、`/api/ping`。仅此五个，其余一律要鉴权。
- **限速**：同一 IP 连续失败 10 次锁 10 分钟，计数在内存（单进程部署够用；多副本要换 Redis）。
- **开放重定向**：`next` 参数只接受站内路径，`//evil.com` 这类一律落回 `/`。

### 为什么非回环监听必须带口令

`cli.py serve` 在启动前检查：`web_host != 127.0.0.1/::1` 且 `web_password` 为空 → 打印错误并 **exit 1**。这比「启动后警告一下」更硬，因为警告会淹没在日志里，而裸奔的研判台等于把正在跟踪的目标清单贴在公网上。

```bash
# 想对外，就必须有口令
SILVER_WEB_HOST=0.0.0.0 SILVER_WEB_PASSWORD=... silver-sentinel serve
# 只给反向代理用，可以不要口令（由 nginx 挡）
silver-sentinel serve --host 127.0.0.1 --port 18700
```

口令留空且监听回环时，若需要强制登录（比如 nginx 反代对外），开 `SILVER_WEB_FORCE_AUTH=1`。

## 三、外网部署

### 两个脚本

| 脚本 | 在哪跑 | 干什么 |
| --- | --- | --- |
| `deploy/push.sh` | 本机 | 取/构建 wheel → tar 流式传输 → 远端调用安装脚本 |
| `deploy/install.sh` | 服务器 | 建账号、建 venv、装 wheel、生成 `.env`、写 systemd、起服务、自检、放行端口 |

```bash
# 一条命令完成更新
bash deploy/push.sh root@<服务器IP>
# 换端口或密钥
bash deploy/push.sh root@<服务器IP> -p 2222 -i ~/.ssh/id_ed25519
```

`push.sh` 先用 `zipfile` 自检 wheel 里有没有 `style.css` / `ui.js` / `login.html`——静态资源漏打包是最常见的「装上了但页面空白」。

### install.sh 的几个设计点

1. **幂等**：反复执行只覆盖程序。`.env` 已存在就不动，只补缺失的键（`ensure_env`）。**口令不会被重置**——升级时把人挡在门外是最糟糕的失败模式。
2. **解释器挑选**：不只看版本，还看 `import venv, ensurepip` 是否可用。Debian 系上 `python3.12-venv` 是独立包，只看版本会挑到一个建不出 venv 的解释器，装到一半才炸。
3. **venv 兜底**：创建失败时自动 `apt install python${V}-venv` / `dnf install python3-pip` 后重试一次，仍失败才报错退出。
4. **systemd 加固**：`ProtectSystem=strict` + `ReadOnlyPaths=/opt/silver-sentinel` + `ReadWritePaths=/var/lib/silver-sentinel`。程序目录只读，只有数据目录可写。被拿下的进程写不进自己的二进制。
5. **数据与程序分离**：程序在 `/opt/silver-sentinel`，数据（SQLite、证据、举报包）在 `/var/lib/silver-sentinel`。删掉程序目录不影响证据链。
6. **自检**：起服务后轮询 `/api/ping` 最多 30 秒，失败直接把 `journalctl -n 40` 打出来，不让用户自己猜。
7. **公网 IP 探测**：依次试 ipify / ifconfig.me / ipinfo，全是内网地址时如实标注「外网请用公网 IP 或域名」。

### 防火墙

脚本会尝试 `ufw` / `firewalld` 放行端口，都没有时只警告。**云厂商的安全组必须手动放行**，这一步脚本碰不到——漏了的表现是浏览器「连接超时」，而不是 404，很容易误判成服务没起来。

### 反向代理（可选）

已有 nginx 时，推荐让项目只监听回环，由 nginx 转发并加 TLS：

```nginx
server {
    listen 443 ssl http2;
    server_name sentinel.example.com;
    ssl_certificate     /etc/letsencrypt/live/sentinel.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/sentinel.example.com/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:18700;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_buffering off;          # 实时流靠 SSE，缓冲会让它看起来卡住
        proxy_read_timeout 3600s;
    }
}
```

`proxy_buffering off` 是必须的：发现流的 SSE 走 chunked，nginx 默认缓冲会把事件攒着不发，界面上表现为「半天不动，然后一次刷出十条」。

此时应设 `SILVER_WEB_FORCE_AUTH=1`，用项目自带的登录页而不是 `auth_basic`——后者无法配合 `?token=` 下载证据包。

## 四、验收清单

部署完成后按顺序过一遍，任何一条不过都别急着对外：

```bash
# 1. 进程活着，版本正确
systemctl status silver-sentinel
/opt/silver-sentinel/.venv/bin/silver-sentinel --version

# 2. 健康检查（不需要口令）
curl -s http://127.0.0.1:18700/api/ping          # {"status":"ok"}

# 3. 未登录必须被挡
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:18700/api/stats   # 401
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:18700/            # 302

# 4. 口令能进
curl -s -H "Authorization: Bearer $PW" http://127.0.0.1:18700/api/stats | head -c 120

# 5. 外网可达（在你自己电脑上跑）
curl -s -o /dev/null -w '%{http_code}\n' http://<服务器IP>:18700/login      # 200
```

第 5 步超时 → 安全组/防火墙；返回 502 → 服务没起；返回登录页但登录后白屏 → 静态资源没进 wheel，回看 `push.sh` 的自检输出。

## 五、已知边界

- **单进程限速**：失败计数在内存，多副本部署时每个副本各算一份。要严格限速得换 Redis 或前置 nginx `limit_req`。
- **口令即密钥**：会话签名密钥由口令派生，所以口令强度直接决定会话可伪造性。脚本生成的是 24 位大小写数字混合，别改成 `123456`。
- **没有多用户**：只有「有口令」和「没口令」两种身份。需要分权（研判员 / 审核员）时得引入用户表，当前版本没做。
- **无 HTTPS**：直连端口是明文 HTTP。口令会以明文过网，公网部署应走 nginx + 证书，或至少套一层内网隧道。
