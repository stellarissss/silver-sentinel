# 试运行报告：30 分钟连续运行验收

> 目的不是「跑通」，而是回答三个问题：**能不能用、够不够广、撑不撑得住**。
> 全程不做人工干预，只观察日志、指标与产物。

---

## 一、环境与方法

| 项 | 值 |
| --- | --- |
| 主机 | 沙箱容器，Ubuntu 22.04 / Python 3.11 |
| 版本 | `silver-sentinel 1.0.0`（分发 wheel 与本仓库同一份代码） |
| 存储 | SQLite（WAL）+ 本地目录副本 `/tmp/sv-replica` |

| 时长 | 01:51:58 → 02:22:38（30 分 40 秒） |

无 LLM、无 ICP、无 Neo4j、无 MobSF —— 这是刻意的：**先证明在最简配置下系统仍然工作**，
能力缺失由运维页如实标注，而不是假装可用。

## 二、结论

| 维度 | 结论 | 依据 |
| --- | --- | --- |
| **可用性** | 通过 | 30 分钟内 24 轮周期零失败，进程无重启，控制台/SSE/指标全程可访问 |
| **广泛性** | 通过 | 处理 56,032 张证书（≈1,830/分钟），命中词根 1,234 次，落库 179 个域名 |
| **精度** | 通过（有噪音，但可控） | 162 个「证据不足」留在候选/冷存未打扰；2 个真阳性被推到 watch/high_risk |
| **可靠性** | 通过 | 事件日志 85 条全部链式校验通过；副本 101 个文件全部回读一致；删行演练精确定位到第 31 行 |
| **归因** | 通过 | 共享证书的两个 APK 被正确归并为一个团伙；共享云基础设施的误聚已修复并在重建后消失 |

一句话：**这套东西可以挂在服务器上长期跑了**，但需要运维者接受「大部分线索是噪音」这一前提——
系统的价值在于把噪音与真阳性的分界线画在可复核的证据上，而不是画在一个分数上。

### 4.4 归因

验收时人工提交两个共享签名证书的 APK，系统自动归并：

```

2 处互相内嵌，2 处同页面模板，2 处同一证书签名；其中 2 项高度可疑
```

注意摘要写的是「凭什么连起来」，而不是「疑似诈骗」。举报时这句话可以直接作为关联证据。

## 六、运行中发现并修复的问题

这部分才是试运行最大的价值——**每一条都是「跑起来才会暴露」的静默故障**。

### 1. CT 日志「冻住了」但指标照涨

现象：接的是 `nimbus2025`，`tree_size` 不再变化，进程正常、速率正常、却什么新证书都拿不到。
原因：CT 日志按半年度滚动，到期后**冻结**。写死的日志清单最多撑半年。
修复：
- 启动时从官方 `log_list.json` 拉当前 `usable` 日志，按可达性并行探测后选择；
- 冻结检测（连续 8 次 `tree_size` 不变即告警），并自动换一条日志；
- 内置清单也更新为当前在跑的日志。

### 2. 请求 256 条只回 100 条，游标却推到了 256 之后

现象：明明在跑，覆盖量却只有理论值的 1/3。
原因：`get-entries` 在负载高时会截断响应；代码把游标推到「请求区间的末端」，
中间没返回的证书就被永久跳过。
修复：游标只按**实际返回条数**推进；不满页就丢弃后续预取的页，下一轮从断点重来。
回归测试守着这条（`test_cursor_advances_by_returned_entries_not_requested_range`）。

### 3. 单批串行 → 永远追不上

现象：一条 30 亿条目的日志每分钟新增约 2,000 条，单线程每轮只取一页（100 条），永远落后。
修复：单日志内**多页并发**（默认 6），多日志**各起线程**；实测吞吐提升到 1,800+ 条/分钟。

### 4. ICP 没配置，却把整条流水线拖死

现象：首轮周期跑了 260 秒，只研判了 7 个资产。
原因：ICP 只判断了「开关」，没判断「服务地址配了没有」，于是每个域名都去令牌桶排队
（10 次/分钟 = 每域 6 秒），40 个目标 = 240 秒。
修复：`icp_ready` 同时要求开关与服务地址；未配置直接返回 `unknown`，不排队。

### 5. 全局限速把并发变成了串行

现象：8 个线程并发研判，全部在同一时刻结束（各 33 秒），像被同一个闸门卡住。
原因：HTTP 客户端用**全局**令牌桶（2 req/s），并发数再多也只能排队。
修复：改为**按目标站点**限速（每站 2 req/s）+ 全局总闸（4×）。同一批 8 个目标降到 4–6 秒。

### 6. OpenPhish 的「6 小时缓存」根本没生效

现象：每个资产都要重新下载一次 feed（2.8 秒）。
原因：函数先下载再写缓存，读缓存的分支从来没走到。
修复：先查缓存，加锁防击穿，源不可用时沿用旧缓存而不是返回「未知」。

### 7. 共享云基础设施被当成了团伙

现象：`*.aws.snowflake.com` 下的几个随机子域被归并成 3 个「团伙」。
原因：云厂商为整个域签**通配符证书**，共用证书在这里没有任何归因价值。
修复：新增共享基础设施后缀表（AWS / 阿里云 / 腾讯云 / Snowflake / Vercel / Cloudflare Pages…），
这类域名照常发现和入库，但**不建证书边、不建解析边**，不参与聚类。
重建后：2 个社区、1 个团伙、1 个跳过——误聚清零。

### 8. 深链打不开对应视图

现象：直接访问 `/#discover` 停在概览页。
原因：只处理了首次加载的 hash，没有监听 `hashchange`。
修复：补上 `hashchange`，并在切换视图时同步地址栏。

## 八、给运维者的三条建议

1. **别盯分数，盯增量**。`confirmed` 数量突然上涨、或 `candidate` 一周涨十倍，才是需要看的信号。
2. **副本一定要放另一台机器**。同机目录副本只防误删，不防磁盘损坏与主机被攻破。
3. **每周做一次删行演练**。`log verify` 通过不代表链路没被动过——只有演练过的恢复流程才算流程。
