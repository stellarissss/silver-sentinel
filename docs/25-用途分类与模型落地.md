# 用途分类：词库保广，模型保细

> 一句话：**词库负责「不漏」，用途分类负责「不吵」。**
> 前者在 CT 流里广撒网，后者在进队列后把客服站、论坛、电商、企业站挡在高危队列之外——
> 但只降档、不删除，任何一条硬证据都能让它立刻翻案。

## 一、为什么换判据

上一轮实测已经说明问题：**同一份词库**对 25 个正规中文站打分，8 个 ≥0.97，
比已知诈骗话术样本（0.990）还高。

| 站点 | 词库分 | 实际用途 |
|---|---|---|
| 央视网健康频道 | 0.990 | 新闻媒体 |
| 39 健康网 | 0.990 | 行业门户 |
| 中国养老网 | 0.983 | 行业门户 |
| 阿里巴巴国际站 | 0.975 | 电商 |
| 53kf | 0.513 | 客服 SaaS |

不是词表不够严，是**建模对象错了**：词库建模的是「涉老行业词汇」，
而正规从业者天天写「养老/补贴/民政」。继续加词只会让误报更多——
这是一个负向的规模效应。

真正的判别信息在**站的形态**：客服 SaaS 有工单/坐席/会话 SDK，
论坛有版块/楼层/回复，电商有购物车/SKU，企业站有产品中心/解决方案。
这些是长期经营沉淀下来的结构，骗子做不出来——他做的是单页落地页、
报名表单、APK 分发。

## 二、三层架构

```
                    ┌─────────────────────────────────────┐
   CT / 域名排列 →  │ 第一层  词库召回（保广）             │  命中一个词就进候选
                    └──────────────┬──────────────────────┘
                                   ↓ 取证（移动 UA + 渲染）
                    ┌──────────────┴──────────────────────┐
                    │ 第二层  用途分类（保细）             │  客服/论坛/电商/企业 → 降档
                    │  规则基线 + 形态模型（二分类）        │  只降不删，硬证据可翻案
                    └──────────────┬──────────────────────┘
                                   ↓
                    ┌──────────────┴──────────────────────┐
                    │ 第三层  风险判定（不变）             │  词库加权 + 冒充 + 结构组合
                    └─────────────────────────────────────┘
```

用途分类**不产生风险分**，只回答一个问题：这个站会不会承载诈骗。
它输出 `purpose` 与 `suppressed`，由 `triage` 决定档位。

## 三、特征层

`features.py`，68 维，全部可从已落库证据重算（`page_html` / `page_text` /
`network` / `forms` / `tls`），不需要重新抓站。

| 组 | 维度 | 说明 |
|---|---|---|
| 文本形态 | 10 | 长度、CJK 占比、重复行率、段落数——区分「正文页」与「模板页」 |
| 词库 | 8 | 只作「行业相关度」，不作可疑度；骗局词单独计数供否决用 |
| 用途词 | 10 | 客服/论坛/电商/企业/新闻/门户/落地页/分发页八组词典 |
| 结构 | 16 | 表单、输入框（密码/手机/证件）、按钮、链接、导航、iframe、canvas |
| 网络 | 8 | 第三方主机、客服 SDK、统计、支付、CDN、POST 目标 |
| 基础设施 | 8 | 域名长度/数字/连字符、高风险 TLD、免费证书、证书剩余天数 |
| 自称 | 8 | claim 等级、机构数、标识码、备案号、冒充标记、APK、二维码 |

三条实现约束：

1. **按唯一主机计数**，不按请求条数。一个页面往 `53kf.com` 发 50 条请求，
   仍然只是 1 个 SDK——早期版本把它放大成「122 个 SDK」，特征直接失真。
2. **按不同词计数**，不按出现次数。长页面天然占优，客服站首页两万字，
   「回复」出现 40 次就能把论坛分刷到天花板。
3. **任何异常退化为 0，不抛异常**。取证链路上一次异常就是一整站白跑。

## 四、模型层

### 为什么是二分类

先试过八分类（客服/论坛/电商/企业/新闻/门户/落地页/分发页），
102 条样本上准确率只有 **0.54**。不是模型不行，是类别边界本身模糊：
新闻站和行业门户结构几乎同构，论坛和企业站都有多级导航。硬分只会互相吞样本。

业务上真正需要的判断只有一个：**这个站的形态会不会承载诈骗**。

- `operational`：有长期经营形态（客服/论坛/电商/企业/新闻/门户）
- `target_shaped`：单页落地、侧载分发——「一个页面劝你做一件事」

具体是哪一种经营形态，交给规则解释——人能看懂，也能改。

### 指标（102 条样本，5 折交叉验证）

| 指标 | 值 | 含义 |
|---|---|---|
| 准确率 | **0.93** | — |
| macro-F1 | **0.88** | 两类都要好，不能靠「全判经营型」刷准确率 |
| 经营型召回 | **0.976** | 客服/论坛/企业站基本都能认出来 |
| 经营型精确 | **0.942** | 判成经营型的里面 94% 真的是 |
| 风险承载召回 | 0.737 | 落地页有 26% 认不出来——**所以规则必须主判** |
| 风险承载精确 | 0.875 | — |

三个候选模型（LogisticRegression / HistGradientBoosting / RandomForest）
自动比 CV macro-F1，本次 RandomForest 胜出（0.879 vs 0.801 vs 0.751）。
换算法只改 `tools/train_purpose.py`，不动线上代码。

| 论坛 | 7 | 虎扑 / 19楼 / NGA / 知乎 / 果壳 / 集思录 |
| 电商 | 13 | 京东 / 当当 / 敦煌 / 中国制造网 / 拼多多 |
| 企业 | 14 | 易歌 / 金蝶 / 泛微 / 汉得 / 东软 / 华为 / 阿里云 |
| 新闻 | 16 | 人民网 / 新华网 / 央视 / 澎湃 / 财新 / 界面 |

## 五、融合：四条硬约束

规则与模型不是投票，是**有方向的约束**：

1. **规则永远生效，模型只是补强。** 模型文件缺失、版本不匹配、sklearn 未装，
   系统照常运行，只是回到规则基线。
2. **模型只能往保守方向改。** 它有两件事可做：
   - **否决误排除**：规则判「企业站」但模型认为 80% 是落地页 → 不排除；
   - **确认弱规则**：规则判「论坛」但置信只有 0.57，模型认为 5% 是落地页 → 加置信；
   - **兜底规则盲区**：规则完全认不出，模型认为 ≤10% 是落地页 → 判经营型。
3. **冲突不排除。** 任何拿不准的情况一律 `unknown`，交回风险判定。
4. **排除只到 `cold`。** 永不 `dismissed`。记录留着，改版、易主、人工复核都能捞回。

融合效果（折外概率，即真实上线会长什么样）：

| | 经营型被识别 | 目标形态被误排除 |
|---|---|---|
| 纯规则 | 31/83（37%） | **0/19** |
| 规则 + 模型 | **57/83（69%）** | **0/19** |

识别率翻倍，误排除仍然为零。这就是「保广」与「保细」同时成立的方式。

## 六、闸门与降级

`triage._purpose_gate()`，位置在冒充判定之后、评分判定之前：

| 用途 | 处置 | 理由 |
|---|---|---|
| 客服 / 论坛 / 电商 / 企业 / 新闻 / 政府 / 经营型 | `cold` | 不占高危队列 |
| 同上，但评分 ≥75 | `candidate` | 宁可多看，不可漏掉一个高分目标 |
| 行业门户（portal） | `candidate` | 门户常被仿冒成「政策资讯站」，保留复访 |
| 落地页 / 分发页 / 未知 | 不干预 | 照常走风险判定 |

闸门**无条件让位**于以下任一事实（`purpose.decide_suppression`）：

- 伪造政府网站标识码 / 伪造备案号 / 冒充机构（`claim.verdict`）
- 命中官方涉诈通报、与已确认团伙共用基础设施
- 页面分发 APK（`apk_links` / `forces_apk_download`）
- 表单索要身份证 / 银行卡 / ≥2 个手机号
- 骗局专属词命中 ≥2（`scam_signature` 簇）

这五条对应的是「骗子会伪装的形态」——他当然会给自己做一个「关于我们」页面。

## 七、训练与迭代

```bash
# 1) 扩充种子集（真实抓取，可 --resume 断点续跑）
python3 tools/build_purpose_dataset.py --resume

# 2) 训练 + 评估（自动比三个算法，输出折外融合评估）
python3 tools/train_purpose.py --report docs/25-附录-模型评估.md

# 3) 查看线上模型状态
silver-sentinel model status

# 4) 分析单个站点（最快的排误报入口）
silver-sentinel purpose https://www.53kf.com
silver-sentinel purpose --asset-id 1234      # 用库内已存证据，不联网
```

**标签回流**是下一阶段的主线：人工标记 `dismissed` 且理由含「客服/论坛/电商/企业」
的资产，自动成为负样本；`confirmed` 且形态为落地页的成为正样本。
数据量到 500 条以上再考虑八分类或替换更强的模型。

**触发重训的条件**（满足任一）：

- 线上 `brief` 的「用途降级比例」连续一周 >75%（闸门可能过宽）；
- `confirmed` 里出现被用途闸门降过档的样本（漏报，最高优先级）；
- 新增一类站点形态（如小程序码页），规则认不出且模型置信低。

## 八、上线与回退

```bash
pip install -U silver-sentinel
silver-sentinel model status              # 应见 available: true 与算法/指标
silver-sentinel purpose https://www.53kf.com   # 应判「客服系统 / 不占队列」
silver-sentinel rescore --retier --limit 3000  # 历史资产补算用途并重新定级
silver-sentinel doctor
silver-sentinel brief --hours 24          # 看「用途分布 / 用途降级」
```

三个开关，都在环境变量里，改完重启 worker 生效：

| 变量 | 默认 | 作用 |
|---|---|---|
| `SILVER_PURPOSE_ENABLED` | `1` | 关掉后完全不做用途判定（只留风险判定） |
| `SILVER_PURPOSE_SUPPRESS` | `1` | 关掉后**只记录不降级**——灰度、线上异常时的一键回退 |
| `SILVER_PURPOSE_MODEL` | 空 | 指定模型路径，便于 A/B 或回滚到旧模型 |

`SILVER_PURPOSE_SUPPRESS=0` 是安全的：用途照常算、照常展示，只是不改变档位。
出问题时不丢数据、不丢判定，改回来即可。

## 九、已知边界

1. **模型只判形态，不判性质。** 一个伪造财政部的站，形态就是落地页——
   模型判对了，但它是不是诈骗，仍然由词库 + 冒充判定回答。
2. **正规业务系统会被判成落地页。** 农机补贴申报平台、租房补贴查询页，
   形态上就是「单页 + 表单」。它们不抑制，走风险判定，最后多半落在 candidate/cold。
   这是可接受的——它们本来也不该占 watch。
3. **论坛识别依赖域名前缀或版块词。** 移动站会跳到 `m.xxx.com`，
   域名前缀失效；正文又没有版块词时（如虎扑首页），只能靠模型兜底判成
   「经营型站点」——档位正确，但用途标签不够精细。
4. **政府站不进训练集**（禁访清单），模型对政府站的判断不可信；
   政府一律走白名单确定性判定。
5. **样本仍然小（102 条）。** 指标应视为量级参考，不是精确值。
   到 500 条以上再谈调参。
6. **不处理「登录墙后面」的内容。** 需要账号才能看的页面，特征只有登录表单，
   会被判成落地页——这也是对的，它不该被排除。
