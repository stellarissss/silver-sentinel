## 二、架构：WebDAV 作为共享后端

```
旧机 node-375a52dc ──┐
                     ├──> 新机 WebDAV (http://43.143.3.160:8089)  ── blobs/ + ledger/
新机 node-b114af31 ──┘         │
                               └── 两机 key_id 相同 → 可互相解密
```

- **共享后端**：新机跑 `wsgidav 4.4.1`（`/opt/ss-dav/run.py`，waitress 作 WSGI server，8 线程），数据目录 `/var/lib/ss-vault-dav`，basic auth（账号 vault，随机 32 字节口令）。systemd 单元 `ss-webdav`。
- **为什么弃用 wsgiref**：wsgiref 单线程处理 PUT 卡死（GET/MKCOL 正常，PUT 超时）。换 waitress 后 PUT 204/GET 200 正常。
- **同一把密钥**：旧机 `vault.key`（key_id 83baf...）复制到新机 `data/vault.key`（0600，属主 sentinel），这是唯一传递的敏感文件。
- **各机独立账本**：node_id 不同，各写各的 `ledger/<node>.jsonl`，无并发写冲突——去中心化设计的核心。

3. **坑**：Ubuntu 24.04 上 install.sh 生成的 `.venv` 目录权限为 700，sentinel 用户无法进入 → systemd 203/EXEC。修复：`chmod -R a+rX /opt/silver-sentinel/.venv`。

5. 新机 env 配 `SILVER_VAULT_{ENABLED=1,BACKEND=webdav,TARGET=http://127.0.0.1:8089,ACCESS_KEY/SECRET_KEY}`。

## 五、发现的待优化项

1. **`WebDAVBackend.list()` 不递归**（`vault.py`）：PROPFIND Depth:1 只列一层，blob 存在 `blobs/<2位>/<sha>.ssv` 两级目录，`list("blobs/")` 返回空。不影响 pull（pull 按账本 blob.name 直接 get），但影响 `dedupe_remote`/状态展示的完整性。建议改为递归 PROPFIND 或对 blob 固定深度做二次列目录。
2. **旧机取证停摆**（v1.16.14 遗留）：`CAPTURE_MIN_FREE_MEM_MB=420` 高于旧机常年 available（<250MB），近 2h 拦截 120 次、100% 拦截，取证自 11/22 21:03 起 0 产出。建议调回 250 或改动态阈值。注意：本次未改旧机此配置（用户只授权改 vault）。
3. **install.sh 在 Ubuntu 的 venv 权限 bug**：umask 077 导致 `.venv` 700，非 root 用户服务起不来。建议 install.sh 里显式 `chmod -R a+rX "$VENV_DIR"`。
4. **wsgiref PUT 卡死**：若自搭 WebDAV 用 wsgiref，PUT 会挂。项目文档若推荐自建 WebDAV，应注明用生产级 WSGI server（waitress/gunicorn）。
5. 新机未装 playwright（`SILVER_SANDBOX_BROWSER=1` 但取证浏览器不可用），当前无取证能力；试验阶段无妨，若要新机独立取证需补装。
