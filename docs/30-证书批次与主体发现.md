# 证书是骗子的注册表（v1.13.0）

> v1.12 从「谁写了这个话术」换到「谁和已知的站共用基础设施」，靠 URLScan 标题
> 检索 + CertSpotter 证书扩散，把涉老资产从 4 条做到 12 条。这一版又换了一次
> 物理量：不再去外部索引里找，而是**直接读目标自己的证书**。

## 二、为什么之前看不见

CT 日志里明明解析了 SAN（`CertObservation.all_domains`），也做了兄弟展开
（`_spread_cert_siblings`），但有三道闸把它挡住了：

| 闸门 | 原值 | 后果 |
|---|---|---|
| `CERT_SIBLING_LIMIT` | 8 | 91 个域名只取 8 个，其余 83 个连记录都没有 |
| `CERT_SIBLING_HINT` | 0.28 | 低于 0.30 的冷存门槛 → 8 个全进冷存 |
| 冷存不排队取证 | — | 进冷存的等不到取证，永远只有域名、没有证据 |

三道闸叠起来：**91 → 8 → 0**。

设计时假设「一张证书挂几个域名」，但事实相反：**站群是批量签发，一张证书
挂一整批**。这个假设错误让最有力的信号完全失效。

## 三、改法：按「批次」判断，不按「单个」

新增 `discover/morph.py::is_bulk_batch`：

```python
BULK_MIN_DOMAINS = 8      # 少于这个数谈不上「一批」
BULK_HOT_SCORE  = 0.60    # 单个域名达到这个分算「随机串」
BULK_HOT_RATIO  = 0.60    # 一批里随机串至少占这么多
```

判据是**比例**，不是「有没有随机串」。这是关键区别：

| 样本 | 形态分达标比例 | 判定 |
|---|---:|---|
| 91 个 `.cn`（oi6o45 那批） | ~95% | **批量站群** |
| 50 个 baidu.com 的 SAN | 0% | 正常（业务域名） |
| 共享主机证书（shop./blog./api.） | 低 | 正常 |

命中批量批次时：

- 展开上限 8 → **60**（CT 侧）/ 详情页侧 80
- 发现权重 0.28 → **0.58**（直接进候选池排队取证）
- 每日展开预算 20 张证书（防止一张证书 60 个 × 每天几十张把队列灌爆）

## 四、第二个洞：入池 8 秒后被自己人压回冷存

改完发现新问题：40 个域名入池 40 秒内变成 `cold`，`capture_state` 还是
`pending`——**一个都没取到证**。

按秒采样定位到 t+8s 开始，每秒 1 个：

```
t+0s  [('candidate', 40)]
t+6s  [('candidate', 40)]
t+8s  [('candidate', 34), ('cold', 6)]     ← 富化流程开始逐个处理
t+14s [('candidate', 28), ('cold', 12)]
```

原因：`pipeline.enrich_asset` 对新资产（`enrich_count == 0`）做富化后调
`triage.apply`。此时资产只有域名、没有正文，评分 0 → 判「证据不足」→ 冷存。
`triage.apply` 的「首次分级可以自由落档」让这件事直接生效。

这正是 v1.12 在 urlscan 线索上踩过的同一个坑。当时的对策是
`meta["await_capture"]`：外部线索取证前不接受域名级降档。这一版把保护范围
从「外部索引」扩到「任何拿到了结构化证据的发现」：

```python
if obs.source in EXTERNAL_SOURCES or score >= STRONG_HINT:   # 0.50
    meta["await_capture"] = True
```

覆盖同 IP 命中（0.78）、批量证书（0.58）、形态池命中（0.5+）。
这些发现的共同点是：**价值在关联，不在页面**，用页面结论否定它们等于自杀。

同一处修复在 `_register_cert_family` 里也做了一遍（那是 capture 侧直接建资产
的路径，不经过 `_persist`）。

## 五、第三个洞：只抓首页，等于只看到诱饵

对 `np4w53.cn` 首页做取证，HTML 里连 `<form>` 都没有——它是一张通告：

> 2026年度个人财政补贴申领通道已开启，请尽快完成申报……名额有限！
> [立即申报]

点进去才看到真正的东西：

```html
<input id="username" placeholder="请输入与身份证一致的姓名">
<input id="idcard"   placeholder="请输入18位有效身份证号码">
<input id="bankcard" placeholder="请输入本人名下有效的借记卡号">
<input id="phone"    placeholder="请输入银行卡预留的11位手机号">
```

提交地址写在 JS 里，**不在任何 `<a href>` 中**：

```js
$.ajax({ url: 'https://d7k2m.cn/submit.php', type: 'POST',
         data: { username: ..., password: user.idcard,
                 captcha_denglu: user.bankcard, captcha_sfshouji: user.phone } })
```

`password` 字段收身份证、`captcha_denglu` 收银行卡——**字段名是对着扫描器
写的**。任何按字段名判断「这是登录页」的规则都会放过它。

新增两件东西：

**1. 第二跳取证**（`sandbox/web.py::_follow_cta`）
找页面上的主行动按钮（申报/领取/立即/下一步/申请…，排除投诉/客服/隐私），
点一下，等跳转，抓新页面。三种导航形态都接住：整页跳转、XHR 后跳转
（`POST api.php → redirectUrl → location.href`）、原地切 DOM。

**2. 端点提取**（`collectors/endpoints.py`）
从 HTML + JS 里挖「数据往哪走」，与「链接到哪」分开：

- 表单 `action`（静态 + 运行时 DOM 两路）
- `$.ajax url:` / `fetch(` / `location.href=`
- 散装 input（没有 `<form>` 包裹的，实测就是这种）
- 字段语义判定：`password` + 「请输入身份证号码」→ 伪装

**3. 后端端点入库**
跨域 + 确实在收敏感信息的端点，单独建一条资产（`discovery_source="backend"`，
`meta["role"]="backend"`），并在 `triage` 里禁止它进冷存——这类域名首页
通常是「站点创建成功」，按内容判必然判空。

## 七、APK 配额改为跟磁盘走

原来写死 `candidate 档 50MB / 日 300MB`，那是「磁盘只剩 6.9G」时代的妥协。
实测涉老诈骗包 80MB 很常见（uni-app 壳 + 加固 + 内置浏览器内核 + 离线视频），
硬卡 50MB 等于只看得见小包，而小包往往只是引流壳。

现在按余量动态给：

| 磁盘剩余 | 单包上限 | 日配额 |
|---|---:|---:|
| < 3G | 80MB | 200MB |
| 3–8G | 150MB | 600MB |
| ≥ 8G | 300MB | 2000MB |

外加一条硬保护：剩余 < 1.5G 直接拒绝下载，明确写进 reason，而不是下到一半
EIO。

## 九、还没解决的

- **第二跳依赖按钮文案**。按钮写「点击核验」能中，「点我」就不中。下一步
  可以退化到「找页面里唯一的按钮」或直接跟进 `api.php` 返回的 `redirectUrl`。
- **字段语义只覆盖常见名**。`sfzh`、`yhkh` 这类拼音缩写认不出，会落到「其他」。
- **后端域名的 IP 没解析**。`d7k2m.cn` 的 `facts.ips` 是空的，同 IP 扩散
  对它无效。证书 SAN 只有 1 个（独立证书），所以它现在是「孤岛」——但它
  的价值本来就在 `serves`，不在扩散。
- **取证速率 3 个/分钟**。80 个域名要 27 分钟，一批证书刚好能消化。如果
  同时来三批就要排队一小时，需要调 `capture_batch` 或做并发。
