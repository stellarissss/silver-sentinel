## 一、先回答你的三个质疑

### 1.1 「怎么比之前还少了？」——是真少了，但数据没丢

11 月 5 日凌晨执行过一次 `discover reconcile --apply`，把词库精度升级后不再命中的存量资产批量改为 `dismissed`。快照能精确到小时：

| 时间 | 资产总数 | 有效（非 dismissed） | 已排除 |
| --- | --- | --- | --- |
| 11-04 21:12 | 1,909 | 1,909 | 0 |
| 11-05 03:52 | 2,460 | **2,460** | 0 |
| 11-05 07:07 | 2,612 | **462** | **2,150** |
| 11-06 22:45 | 2,993 | 843 | 2,150 |

三小时十五分钟里，**有效池从 2,460 掉到 462，降幅 87%**。这 2,150 条的去向：

| 原因 | 数量 | 是否合理 |
| --- | --- | --- |
| 词库精度升级：旧版子串匹配误报，不含有效词根 | 1,260 | 合理，确属误报（`people`、`minge`、`-mz11195` 之类） |
| 共享基础设施：平台分配的随机主机名 | 812 | 合理，snowflake / ngrok 等 |
| 同一注册域已有主资产，子域归并 | 78 | 合理，证据保留在主资产 |

**问题不在清洗，而在清洗之后没有告诉任何人**：
- 概览的「线索总数」仍把 2,150 条 dismissed 算进去（2,993），
- 「近 7 天新增」因为数据只跑了 3 天，等于总数（2,993），看起来永远不动，
- 没有「本次清理 2,150 条、原因分布如何」的任何提示。

结果就是你看到的撕裂：总数很大、能用的很少、数字还不动。

### 1.2 「风险指数也低了」——目前没有风险指数，你看到的是三个失真数字

代码里从来没有「风险指数」这个指标（全仓库检索无此字段）。概览上是五个绝对值，其中三个失真：

| 指标 | 现在显示 | 真实情况 |
| --- | --- | --- |
| 线索总数 | 2,993 | 有效只有 843；2,150 条早已排除 |
| 待处置（高危及确认） | 33 | 其中 **11 条是 dismissed**，只是 verdict 还留着 `high_risk` |
| 近 7 天新增 | 2,993 | 等于总数，因为全库都在 7 天内 |

真实分数分布：dismissed 平均 10.1，candidate 平均 20.6，cold 平均 0.2，watch 平均 49.3；真实域名最高分 **38.8**，唯一 70.3 是内置的示例 APK。所以「风险看起来低」不是错觉——**91.3% 的资产是「证据不足」**，因为系统几乎没看过页面内容。

### 1.3 「没有新增」——有，但每小时约 14 条，且进不了视野

发现引擎没停：7.8 小时处理 401,905 张证书，匹配 17,088 次，去重后真正入库 107 条，约 **13.7 条/小时**。

漏斗卡在三个地方：

| 阶段 | 数量 | 说明 |
| --- | --- | --- |
| 已解析证书 | 401,905 | 3 个 CT 日志，其中 1 个已冻结 |
| 命中词根 | 17,088 | 4.25%，词库 362 词 |
| 同域去重 | 16,929 被挡 | 同一注册域反复签发 |
| 通过阈值入池 | 107 | 约 14 条/小时 |
| 进入「待处置」视野 | 约 3 条/天 | 分数 <20 的一律沉底 |

新增不是没有，是**新增的目标没有证据、没有判定、没有下一步**，所以在界面上等于不存在。

## 二、五个断点：为什么达不到「发现、监控、评估」

| # | 环节 | 现状 | 根因 | 代码位置 |
| --- | --- | --- | --- | --- |
| 1 | 发现 | 14 条/小时，91% 判定不足 | 只靠 CT 关键词命中；362 词；单注册域去重后只剩个位数 | `discover/engine.py` `_on_ct_batch` |
| 2 | 取证 | **页面证据 0 条** | 域名入库只做 RDAP / DNS / URLhaus / OpenPhish / ICP，从不打开页面 | `intake.py` `_collect_url_facts` |

| 4 | 评估 | 只看名字，不看内容 | 45 条规则全靠域名/证书/备案特征；LLM 未配置 | `scoring/engine.py`、`config.py` |
| 5 | 闭环 | 团伙 0、监控 0、举报 0 | 团伙要求社区内 ≥2 个 score≥35；watch 只有 3 个；WatchTarget 只能手动建 | `graph/community.py`、`monitor.py`、`api.py:576` |

### 2.1 取证其实写好了，只是没人调用

`pipeline.probe_web()` 已经能一次落四份证据：正文、HTML 原文、首屏截图、运行时网络请求。但它只挂在两个手动入口上：

- `POST /api/assets/{id}/probe`（资产详情里点一下）
- `silver-sentinel probe <id>`

`run_cycle()` 里没有它，监控调度里也没有它。线上 1,757 条证据的实际构成：

| 证据类型 | 条数 |
| --- | --- |
| assessment（研判快照 JSON） | 1,756 |
| apk（示例安装包） | 1 |
| page_html / screenshot / network | **0** |

### 2.2 团伙为什么永远是 0

每轮聚类都能找出 10 个社区，但每轮都 `skipped: 10`：

```python
suspicious = [a for a in asset_nodes
              if a.tier in (CONFIRMED, WATCH) or a.score >= 35]
if len(suspicious) < 2 and not confirmed:
    skipped += 1
    continue
```

全库只有 3 个 watch、33 个 high_risk，且分散在 10 个社区里。**要求每个社区至少 2 个高分资产，在当前数据分布下永远凑不齐。**

### 2.3 监控为什么是空页

`WatchTarget` 只有两个创建入口：`POST /api/watch` 和 `silver-sentinel watch add`。发现、研判、分级都不会自动创建。所以「监控」页永远显示「还没有监控目标」。

### 2.4 当前能力自陈（`/api/health`）

| 能力 | 状态 | 含义 |
| --- | --- | --- |
| `sandbox_web` | **false** | `no-proxy`，页面执行被出口策略拒绝 |
| `sandbox_apk` | static-only | 只做静态解析，不跑动态沙箱 |
| `egress` | **blocked** | 无代理时 fail-closed，不碰可疑目标 |
| `llm` | off | 未配置模型 |
| `ct_stream` | true | 发现引擎在跑 |
| `icp` | true | 备案查询可用（但有风控） |

服务器条件其实够用：Chromium 1248 已安装，磁盘 50G 用 37G、剩 11G，内存 2G（可用约 600M）。**缺的只是出口策略和编排。**

但还有一个隐藏问题：Chromium 装在 `/root/.cache/ms-playwright/`，而服务以 `silver` 用户运行，看不到这份浏览器。即使现在打开出口，第一次执行也会报「浏览器不可用」。P1 需要把浏览器装到服务可读路径，或显式设置 `PLAYWRIGHT_BROWSERS_PATH`。

## 三、目标：把「流水」变成「闭环」

现在的系统是一条直线：`发现 → 入库 → 打分 → 结束`。要变成环：

```
发现 → 快筛 → 取证 → 评估 → 分级 → 监控 → 变更 → 再评估
                                      ↓
                                   团伙归并 → 举报材料
```

### 3.1 可验收的目标（P2 结束时）

| 环节 | 指标 | 现在 | 目标 |
| --- | --- | --- | --- |
| 发现 | 新候选/小时 | 14 | ≥60，相关率 ≥25% |
| 发现 | 发现→入库时延 | 分钟级 | <5 分钟 |
| 取证 | candidate 及以上取证覆盖率 | 0% | ≥95% |
| 取证 | 页面证据类型 | 0 种 | HTML + 截图 + 网络 + 证书 + APK（有则下） |
| 评估 | 全库「非证据不足」占比 | 8.7% | ≥60% |
| 监控 | watch/confirmed 纳入周期复访 | 0% | 100% |
| 监控 | 变更（改版/换域/换包/下线）发现时延 | 无 | <30 分钟 |
| 评估 | 团伙数 | 0 | ≥10，且每个可解释 |
| 运营 | 每日自动报告 | 无 | 1 份 |

### 3.2 风险指数怎么定义

不再拍一个黑箱数字，用四项可解释的加权，并在旁边同时显示绝对值：

```
风险指数 = 0.40 × 高危占比
         + 0.30 × 近 24h 高危新增速率（归一化）
         + 0.20 × 证据完备率
         + 0.10 × 监控覆盖率
```

每项都能点开看构成。趋势按 7 天画，避免「今天高明天低」的误读。

## 四、方案

### 4.1 发现层：扩量，但先快筛

**扩量（三条路，按性价比排序）**

1. **词库扩到 800+**：现有 362 词根，补品牌（银行、保险、药企、平台）、地区（省+市+「老龄委」「老干部局」）、政策（国补、惠民、乡村振兴、共同富裕）、话术（领鸡蛋、签到返利、拉人头）。中文自动派生拼音、繁简、常见错拼。
2. **组合生成**：复用已有 `collectors/typosquat.py`，按 `品牌 × 主题 × 地区` 生成候选域名，直接做 DNS 探测，不依赖 CT 是否签发。
3. **新发现源**：
   - APK 内嵌域名回灌（现有字段 `meta.domains` 已采集，但从未入发现队列）
   - 落地页外链、下载域名、客服域名（取证时顺带产出）
   - 公开通报导入（12377 / 12321 / 公安部名单）
   - 短链与二维码（取证时解析）
   - ICP 新备案（已有客户端，目前只用于查询，不用于发现）

**快筛（避免又一次 2,150 条误报）**

命中词根不再直接入库，先过三道廉价闸门：DNS 是否存在、注册天数、是否备案。三条都不满足的进 `cold`，不占取证配额；满足一条的进 `candidate`，进入取证队列。

**指标面板**：`seen → matched → deduped → screened → admitted` 五段漏斗，每小时一行。现在运维页只有总数，看不出卡在哪。

### 4.2 取证层：Evidence Pipeline（复用 `probe_web`，不改沙箱内核）

**任务化**

新增 `capture_tasks` 表：`asset_id / priority / state / attempts / next_run_at / error`。
`run_cycle()` 每轮取 N 条（默认 8 条）派发；单进程串行执行（2G 内存跑不了并发 Chromium）。

优先级：`confirmed > watch > candidate(score 高) > candidate(新)`；`cold` 不取证。

**采什么（每个资产一份「证据矩阵」）**

| 证据 | 说明 | 体积控制 |
| --- | --- | --- |
| `page_html` | 最终落地页 HTML 原文（含重定向链） | 8MB 上限，gzip 存 |
| `page_text` | 正文纯文本 | 2MB |
| `screenshot` | 首屏 + 全页，WebP | 单张 ≤400KB |
| `network` | 运行时请求（含 POST 外传地址） | 500 条上限 |
| `tls_cert` | 证书链、签发者、SAN、指纹 | 小 |
| `dns` / `rdap` / `icp` | 解析、注册、备案 | 小 |
| `forms` | 表单字段与提交地址 | 小 |
| `qrcode` | 页面二维码解码出的链接 | 小 |
| `apk` | 安装包源文件（见下） | 默认 50MB 上限 |

采集失败也落一条 `capture_error`，写清原因（超时/403/证书错误/出口拒绝），**不能静默**。

**APK 下载**

新增 `collectors/apk_fetch.py`，复用 `sandbox/apk.py` 的静态分析：

1. 从页面 `apk_links`、`downloads`、`.apk` 正则、二维码里收集候选链接；
2. `HEAD` 看 `Content-Type` / `Content-Length`，超过上限直接记录「拒绝下载（超限）」；
3. 流式下载到临时文件，边下边算 SHA-256，限制总时长与速度；
4. 校验 ZIP 魔数，落 `vault` 加密副本 + `evidence` 原始文件；
5. 静态分析：包名、签名证书、权限、内嵌域名/URL、收款地址、模板指纹；
6. **不执行、不安装**；文件名用哈希，不用对方给的名字。

默认策略建议：`watch` / `confirmed` 自动下载；`candidate` 只下 ≤10MB 的；单日总量上限 300MB。这一条需要你拍板（见第六节）。

**证据矩阵 UI**

资产详情新增「证据」页签，六格矩阵直接显示「有/无/失败原因」：

```
页面 HTML ✓  截图 ✓  网络 ✓  证书 ✓  APK —（未发现）  备案 ✓
```

每格可预览、单条下载；顶部「全选 / 导出 ZIP / 删除」。

**选择性获取**

- 单条：`GET /api/evidence/{id}/download`
- 整套：`GET /api/assets/{id}/evidence.zip`
- 批量：`POST /api/evidence/export`（按筛选条件打包，后台生成，完成后给下载链接）
- 命令行：`silver-sentinel evidence pull --asset <id> --out ./cases/`

### 4.3 评估层：让内容参与判断

**新增 10–12 条内容规则**（都要求证据里能引用原文）：

| 规则 | 例子 |
| --- | --- |
| 政策伪装 | 「国家惠民」「乡村振兴补贴」「民族资产解冻」+ 领取入口 |
| 收益承诺 | 「签到返利」「每日收益」「拉人头奖励」 |
| 身份冒充 | 「老龄委」「民政部指定」「xx 银行合作」 |
| 下载诱导 | 「浏览器打不开，请下载 APP」「扫码安装」 |
| 收款诱导 | 页面出现银行卡号、USDT 地址、个人收款码 |
| 客服话术 | 复制微信号、QQ 群、Telegram |
| 表单收集 | 身份证、银行卡、验证码字段 |
| 域名异常 | 新注册 + 无备案 + 境外主机 + 仿冒品牌 |

**LLM 只做灰区**：分数 25–70 且证据齐全的才调用，输出必须引用证据 ID；其余走规则，控制成本。

**判定必须带证据引用**：`{"verdict": "high_risk", "because": ["evidence:1234 页面标题", "signal:KW-001"]}`。

**团伙两级**

| 层级 | 条件 | 展示 |
| --- | --- | --- |
| 关联簇（cluster） | 共享证书 / 模板 / 收款地址 / 内嵌域名 / 同名品牌，≥2 个资产 | 直接展示，标注「待确认」 |
| 确认团伙（campaign） | 关联簇内 ≥2 个 watch/confirmed，或 ≥1 个官方通报 | 进入处置流程 |

这样既不会因为门槛太高永远为空，也不会把「共用一台 CDN」当成团伙。

### 4.4 监控层：自动纳管 + 变更检测

**自动建目标**：`triage` 产出 `watch` / `confirmed` 时，同事务写入 `WatchTarget`（配额 200，按分数排序，超出后淘汰最低分）。

**复访周期**：`confirmed` 2h、`watch` 6h、`candidate` 72h；连续 3 次失败自动退避到 24h。

**变更检测**（每次复访比对）：

| 维度 | 方法 | 触发 |
| --- | --- | --- |
| 页面内容 | HTML 去标签后 simhash | 相似度 <0.9 |
| 视觉 | 截图 dHash | 汉明距离 >8 |
| 证书 | fingerprint / issuer / SAN | 任一变化 |
| 解析 | A 记录集合 | 任一变化 |
| 安装包 | 下载链接或 SHA-256 | 变化 |
| 状态 | HTTP 状态 / 域名是否解析 | 下线 / 复活 |

变更写入 `signals` + 事件流，并按方向调整 tier（改版升级、下线记录为处置效果）。

**监控页**：在盯清单（目标、tier、上次/下次、最近变更、失败原因），不再是一张空表。

| 线索库混入已排除项 | 默认只看「有效」，提供 tier 筛选与列；dismissed 单独入口；显示总数与分页 |
| 证据看不见 | 资产详情加「证据」页签 + 矩阵 + 预览/下载/删除 |
| 不知道下一步 | 每个资产顶部给一个主行动按钮：`立即取证` / `加入监控` / `生成举报材料` |

每页的一行说明（直接可用的文案）：

| 页面 | 说明 |
| --- | --- |
| 概览 | 今天的总体风险、待办和异常，先看这里再去具体页面 |
| 发现流 | 引擎正在从 CT 日志里看到什么，哪些被收进来、哪些被丢弃、为什么 |
| 研判台 | 手动输入一个链接或安装包，得到评分、判定和逐条依据 |
| 线索库 | 全部目标的检索与筛选；默认只显示有效目标，已排除单独查看 |
| 关系图谱 | 域名、证书、安装包、收款地址之间靠什么连在一起 |
| 团伙 | 共享基础设施的一组目标，按关联强度排序；关联簇待确认，确认团伙可处置 |
| 监控 | 正在盯的目标、下次复访时间、最近一次变化 |
| 运维 | 引擎、取证队列、证据链和存储的健康状况 |
| 规则库 | 评分规则与词库；改动会直接影响判定结果 |

### 4.6 存储与删除策略

**存储分层**

| 层 | 内容 | 位置 |
| --- | --- | --- |
| 热点 | 近 30 天 candidate 及以上 | `data/evidence/` + `data/vault/` |
| 冷存 | 30 天前、cold / dismissed | 同盘，压缩归档，UI 仍可查 |
| 外部 | 可选 S3 / WebDAV / 本地拉取 | `vault` 已有 backend 抽象，直接复用 |

按当前采集量估算：每资产 HTML+截图+网络约 80–120KB（压缩后），当前约 330 条/天 ≈ 33MB/天 ≈ 1GB/月，11G 可用能撑大半年；扩量到 60 条/小时后 ≈ 4GB/月，需要压缩配额或外置归档。**APK 是唯一会迅速吃满磁盘的**，必须单独配额。

**删除规则（按你的要求）**

- 默认**永久保留**；`dismissed` 不自动删证据。
- 删除只有两个入口：① 人工确认「不是目标」时勾选「同时删除证据」；② 证据页手动删除。
- 删除是**软删除**：`deleted_at / deleted_by / delete_reason`，文件移到 `trash/`，保留 7 天；链上写一条 tombstone，`verify` 仍能通过。
- 7 天后物理清除需再次确认，或由定时任务在「已确认非目标」前提下清理。
- 每次删除写审计事件，可在运维页查。

## 六、需要你拍板的关键决策

### 1. 取证出口怎么走

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 服务器直连 | 立刻可用，零成本 | 暴露服务器 IP；可能被目标封禁或报复；部分站点按 IP 地域返回假页 |
| B. 境外 SOCKS5 代理 | 不暴露真实 IP；可绕地域 cloaking | 需要你提供代理；增加一跳延迟 |
| C. 本机采集 Agent | 用你家宽带 IP，最像真实用户 | 需要一台常开的电脑；要写同步协议 |

**建议 B**，没有代理时退 C；A 只作为临时验证。

### 2. APK 自动下载到什么程度

- 上限：默认 50MB/个，可改。
- 范围：只对 `watch`/`confirmed` 自动下？还是 `candidate` 也下？
- 日配额：建议 300MB/天，超出排队到次日。

### 3. 发现扩量的边界

- 是否提供重点品牌/地区/关键词清单（例如某省、某银行、某保健品品牌）？
- 能接受多少误报？「先收后筛」意味着候选池会明显变大，但取证配额有限，需要定优先级。

### 4. 证据保留与删除权限

- 默认永久保留 + 手动删，是否符合预期？
- 是否需要「确认非目标后自动清理 30 天前的截图/APK」以省空间？
- 删除权限只给登录用户，还是需要一个独立的「管理员口令」？

### 5. 要不要接 LLM，接哪家

「不智能」有一半是因为现在完全没有语义理解。规则能覆盖结构化特征，但页面正文里的新话术、隐晦承诺、客服诱导，需要模型。

| 方案 | 说明 |
| --- | --- |
| 国产 API（DeepSeek / 通义 / 豆包） | 中文便宜、延迟低；需要你给 key |
| OpenAI / Claude | 效果稳，成本高，跨境调用有合规问题 |
| 不接，纯规则 | 零成本；灰区继续判「证据不足」 |

建议只对「证据齐全 + 分数 25–70」的灰区调用，单条页面正文先脱敏（手机号、身份证、银行卡）再送出去，成本可控。

## 七、风险与边界

1. **法律与安全**：只做只读访问，不提交表单、不登录、不执行 APK；下载的样本加密存储、不双击、不运行。
2. **IP 暴露**：直连可疑站点会让服务器 IP 进入对方日志；建议代理或本机采集。
3. **资源**：2G 内存跑 Chromium 必须串行，单次超时 30s；如需并发要升配到 4G。
4. **磁盘**：11G 可用，当前页面证据约 1GB/月可承受；扩量后需配额或外置归档，APK 必须限流，否则一周就满。
5. **合规**：证据含个人信息时，导出物需脱敏（现有 `opsec` 已做自身标识清理，受害者信息还需一层）。
6. **不要重复造轮子**：取证复用 `sandbox/web.py`、`probe_web`、`vault`、`evidence` 链；APK 复用 `collectors/apk.py`；团伙复用 `graph/community.py`，只改阈值与展示层。
