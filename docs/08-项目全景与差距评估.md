# 项目全景与差距评估

> 版本 v1.1 · 2026-11-04
> 这份文档回答三个问题：**现在做到哪一步、技术上是怎么成立的、还差什么。**
> 不修饰、不邀功；能跑的说能跑，降级的说降级。

---

## 一、结论先行

1. **它已经是一套"能挂在服务器上长期跑"的系统，而不是演示程序。**
   常驻发现、周期研判、加密取证、图谱归因、证据异地副本、运维自陈、systemd 托管，全部打通。
2. **发现能力从"单点关键词"变成"三路冗余"。** CT 日志直连为主路，certstream 为补强，
   域名排列 DNS 探测为自主兜底；词库 363 词根 / 6 语义簇，中文自动派生拼音。
3. **证据链从"数据库字段"变成"可独立复核的保管链"。** 原始文件 AES-256-GCM 加密、
   内容寻址；仓库侧只留 SHA-256、逐条哈希链、保管链；新设备拉取即可重建全部历史。
4. **最大的三个短板**：ICP 备案判定未接（需要自建服务）、网页/APK 动态取证在当前服务器
   未端到端跑通（无浏览器、无 MobSF）、出站代理未配置导致主动探测按 fail-closed 关闭。
   这三项都属于"外部依赖/资源"问题，不是架构问题。

## 三、技术架构

### 3.1 数据流

```
              ┌──────────────── 发现层 ────────────────┐
 CT 日志 ────▶│ 证书解析 → 域名归一 → 词库匹配 → 去重   │
 certstream ─▶│ → 分级 candidate → 入队研判            │──┐
 DNS 排列 ───▶│                                        │  │
 手工/情报 ──▶└────────────────────────────────────────┘  │
                                                           ▼
              ┌──────────────── 研判层 ────────────────┐
              │ 规则 44 条 + 词库暗示 + LLM(可选)       │
              │ → 风险分 / 置信度 / 判定 / 依据列表     │
              │ → tier: watch / confirmed / cold        │
              └───────────────┬────────────────────────┘
                              ▼
        ┌────────── 取证层 ──────────┐      ┌──────── 归因层 ────────┐
        │ 沙箱网页 / APK / 截图       │      │ 图节点 20 类 / 边 17 种 │
        │ → 证据文件 → AES-GCM 密文   │      │ → 连通分量 / Louvain    │
        │ → 账本 + 保管链 → 副本/多端 │      │ → 团伙 / 主体 / 基础设施│
        └──────────┬─────────────────┘      └───────────┬────────────┘
                   ▼                                    ▼
        ┌──────────────────── 处置与运营 ────────────────────┐
        │ 举报材料（脱敏）· Web 控制台 · SSE · Prometheus     │
        │ 任务记账 · 能力降级自陈 · systemd 托管              │
        └─────────────────────────────────────────────────────┘
```

### 3.2 关键设计决策

| 决策 | 替代方案 | 为什么选它 |
| --- | --- | --- |
| 命中一个词就入库 | 高分才入库 | 骗局域名寿命以周计，等分数够了已经换站；错杀成本只是存储 |
| 分级与评分分离 | 单一 verdict | 评分会随新证据变，分级只升不降（除非有据排除），避免"今天可疑明天清白"的抖动 |
| CT 直连为主、certstream 为辅 | 只用 certstream | 公共实例经常不推流；直连日志可控、可测、可追平 |
| 每个节点一条账本 | 共享一个 manifest | 多端写同一文件必然冲突；按节点分文件后合并只靠内容哈希去重 |
| 账本与密文分离 | 全放 Git / 全放数据库 | Git 适合小文本、强审计；密文适合对象存储；混在一起两边都做不好 |
| 出站 fail-closed | 默认直连 + 提示 | 暴露一次就是永久暴露；少抓一条只是少一条证据 |
| 沙箱必须走代理 | 直连跑浏览器 | 浏览器会泄露 IP、WebRTC 内网地址、TLS 指纹，是最强的身份暴露面 |
| 内置图引擎为默认 | 强依赖 Neo4j | 单机零依赖可跑；规模上来再切 Neo4j，接口一致 |

### 3.3 发现层：三路怎么分工

| 路径 | 覆盖 | 延迟 | 代价 | 现状 |
| --- | --- | --- | --- | --- |
| CT 日志 `get-entries` | 所有公开证书，含随机域名 | 分钟级 | 需追平、会被限流 | 主路，约 440/min |
| certstream WebSocket | 同上，聚合流 | 秒级 | 依赖第三方可用性 | 可连，常不推流 |
| 域名排列 + DNS | 骗子起名惯性（国科/中科/惠民…） | 小时级 | 只覆盖可猜测组合 | 139 个种子，20/300 命中 |
| crt.sh 历史检索 | 已签发但未进当前窗口 | 按需 | 单次最长 70 秒 | 已接入，quick 模式跳过 |

**为什么关键词要宽**：`国科`、`中科`、`惠民`、`乡村振兴`、`民族资产`、`养老`、`补贴`、`免费领`、
`签到`、`返利` 这些词单独看都很正常，但组合上"仿冒权威 + 利益诱导 + 老年群体"就是骗局的骨架。
词库按 6 个语义簇组织，允许跨簇组合加权，而不是简单 OR。

### 3.4 归因层：为什么边权这样定

伪造难度决定证据强度：

| 关系 | 权重 | 理由 |
| --- | --- | --- |
| 同证书（`HAS_CERT` 共享指纹） | 0.90 | 证书私钥只有一方持有，共用几乎等于同一运营者 |
| 同钱包地址 | 0.85 | 收款地址是资金归集的硬标识 |
| 同备案主体 | 0.70 | 主体可能被冒用，但仍是强关联 |
| 同模板指纹 | 0.65 | 同一套源码/页面模板，可能是同一卖家 |
| 同 IP | 0.35 | 共享云 IP 太常见，单独不足以成团 |

共享基础设施（`*.amazonaws.com`、`*.vercel.app`、`*.snowflake.com` 等）**不建证书/解析边**，
否则整朵云会被判成一伙——这是 v1.0 修过的一个真实误聚。

### 3.5 证据层：三条链各管什么

| 链 | 位置 | 作用 | 断链意味着 |
| --- | --- | --- | --- |
| 事件日志链 | `data/events.jsonl` | 记录"系统做了什么判断" | 业务过程被改过 |
| 证据账本链 | `data/ledger/<node>.jsonl` | 记录"有哪些证据、内容摘要" | 证据清单被增删改 |
| 保管链 | `data/ledger/custody-<node>.jsonl` | 记录"谁在何时对证据做了什么" | 经手过程不可信 |

三者独立校验、互相印证；详细设计见 `docs/09-证据保管与多端同步.md`。

## 四、整体图景

### 4.1 三类使用者

| 角色 | 怎么用 | 需要什么 |
| --- | --- | --- |
| 个人研究者 | 单机 + 私有目录后端；每天看一次发现流与高分目标 | 一台 2C2G 服务器 |
| 小型团队 | 每人一台节点，共享 S3/WebDAV 证据仓；账本进私有 Git | 对象存储 + 统一密钥 |
| 社区/机构 | 一台常驻采集节点 + 多台分析节点；举报材料人工复核后提交 | 代理出口、ICP 服务、MobSF |

### 4.2 一天的使用节奏

```
00:00  常驻发现持续跑，候选自动入库
08:00  看 /api/stats：新增高分目标、待复核队列
09:00  对 watch/confirmed 目标做 enrich --probe（有代理时）或人工打开核对
11:00  生成举报材料 → 人工复核 → 提交 12321/12377
14:00  图谱重建 → 看是否有新团伙形成、是否与已知主体相连
18:00  vault verify + log verify，确认两条链完整
每周   vault export → 私有仓库提交；副本异机校验
```

### 4.3 与执法/监管的接口

系统输出的是**线索包**，不是定性结论：

- 被举报对象：域名/APK/账号 + 关联主体 + 基础设施；
- 事实经过：按时间排列的采集记录；
- 判定依据：逐条规则、权重、置信度；
- 证据清单：SHA-256、采集时间、保管链；
- 法条与诉求：按渠道模板生成。

材料末尾明确写明"线索而非定性，最终认定以有权机关调查结果为准"。

## 五、不足评估

按"影响 × 修复难度"排序。每条给出现状、影响、建议。

### A. 覆盖与召回

| # | 问题 | 现状 | 影响 | 建议 |
| --- | --- | --- | --- | --- |
| A1 | ICP 备案未接 | `icp=false`，所有域名 `unknown` | 无法自动判断"是否有备案、备案主体是谁"，主体归因少一条强线索 | 部署 `ICP_Query_lite` / `icpquery-mcp`，配 `SILVER_ICP_API`；这是**投入产出最高**的一项 |
| A2 | CT 只跟 3 条日志 | 全球 usable 日志数十条 | 覆盖率约 10–15%，长尾日志里的证书看不到 | 提到 6–8 条（注意 CPU/带宽），或按运营商分散 |
| A3 | 私域不可见 | 微信群、公众号、小程序、客服号 | 真正的转化与收割发生在私域，公开数据只能看到入口 | 增加"线索导入"：受害者截图/聊天记录结构化录入，纳入同一证据链 |
| A4 | 词库仍以中文词根为主 | 363 词根 | 方言、错别字、谐音、英文/拼音混写覆盖不足 | 引入编辑距离与拼音模糊匹配；用已知样本做召回回归集 |
| A5 | 域名排列组合有限 | 前缀×后缀，139 种子 | 对随机命名无效（本来靠 CT） | 保持现状，把算力留给 CT |
| A6 | certstream 不可靠 | 连上但不推流 | 秒级通道实际缺失 | 自建 `certstream-server-go`，或直接放弃这条补强 |

### B. 取证深度

| # | 问题 | 现状 | 影响 | 建议 |
| --- | --- | --- | --- | --- |
| B1 | 网页沙箱未端到端 | 代码就绪，服务器无 Playwright、无代理 | 拿不到 cloaking 后的真实页面、JS 跳转、表单地址 | 装 Playwright + 配隔离出口；或把沙箱放到独立节点 |

| B3 | 无截图/录屏 | 只有文本与 HTML | 举报材料说服力弱 | 沙箱跑通后加 `page.screenshot()`，进同一证据链 |

### C. 归因与主体

| --- | --- | --- | --- | --- |
| C1 | 强标识缺失 | 主要是域名/证书/模板 | 只能到"团伙"，难到"人" | 接入备案主体、支付账号、手机号（合法来源），图上补 `OPERATES` / `OWNS` 边 |

| # | 问题 | 现状 | 影响 | 建议 |
| --- | --- | --- | --- | --- |

## 六、路线图

### P0（一周内，直接提升可用性）

1. **接 ICP 服务**：`ICP_Query_lite` 起在 127.0.0.1，配 `SILVER_ICP_API`，把 `icp_status/entity` 填满。
2. **配出站代理**：至少一个 SOCKS5；把 `SILVER_OPSEC_ALLOW_DIRECT` 保持 0，验证 suspect 走代理。
3. **装 MobSF**：`SILVER_MOBSF_URL/KEY`，APK 从静态推演升级为动态报告。

### P1（一个月内，补覆盖与闭环）

4. CT 日志扩到 6–8 条，按运营商分散；加"零产出/冻结"告警。
5. 线索导入：受害者截图/聊天记录结构化，进同一证据链。
6. 告警 webhook：高分目标、发现停摆、副本失败、账本断链。
7. 规则回归集：200 条标注样本，CI 跑指标。

### P2（季度级，走向主体归因）

8. 图上补强标识（备案主体、支付账号、手机号），边加时间维度。
9. 跨节点联邦查询：不合并原始数据，只交换账本摘要与主体指纹。
10. 沙箱集群：独立节点跑浏览器/真机，采集节点只做发现与固化。

## 八、一句话总结
