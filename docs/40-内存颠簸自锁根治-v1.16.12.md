# 内存颠簸自锁：卡死反复复发的真正根因与根治 — v1.16.12

日期：2026-11-21

## 背景：v1.16.11 没有真正解决问题

v1.16.11 修了「失败站超时被误分 transient、10 分钟重试」，但部署后服务**仍反复卡死**。
继续取证发现上一个版本对根因判断不完整。

## 真正的根因：取证超时 → swap 颠簸 → 自锁

用内核栈（`do_swap_page` → `__lock_page_or_retry`）钉死了因果链：

1. 1.9G 内存机器上，主进程 RSS 随取证持续增长（645MB → 726MB → 780MB → **1.3G**）；
2. 内存见底 → swappiness 哪怕降到 10，页仍被换出到 swap；
3. 取证线程执行时所需页已被换出 → 触发 `do_swap_page` → **卡在磁盘 IO（D 状态）**；
4. `future.result(timeout=90)` 超时 → `_reset_capture_pool()` 重建线程池；
5. **旧实现只换线程池，不关闭卡死的 Chromium** → 旧线程仍攥着几百 MB，新线程又拉起一个 Chromium；
6. 每次超时累积一组浏览器 → RSS 一路涨 → 更多 swap → 更多 D 状态 → 更多超时。

这是**自锁的死亡螺旋**：越想通过「超时重建」自愈，内存越少、卡得越死。
表现：取证队列 done 计数 6 分钟纹丝不动（取证线程卡死），API ping 从 0.01s 恶化到 26s。

### 为什么降 swappiness / 关 zram 都没用

- swappiness 100→10：只是降低换页倾向，内存真实不足时照样换；
- 关 zram0：2G 压缩 swap 的内容转移到磁盘 swap，`do_swap_page` 从「压缩内存」变成「真磁盘 IO」，更慢；已恢复。
- 根子不是 swap 配置，而是**内存不够时还硬要拉 Chromium**。

## 根治（v1.16.12，代码）

| # | 文件 | 改动 |
|---|---|---|
| 1 | `config.py` | 新增 `capture_min_free_mem_mb`（默认 350，可 env 覆盖），内存看门狗阈值。 |
| 2 | `capture.py` | 新增 `available_memory_mb()`（读 MemAvailable）、`memory_ok()`；读不到返回宽松大值，不挡取证。 |
| 3 | `worker.py` | `CaptureWorker.tick()` 取证前查内存：低于阈值则**跳过本轮**，不灌任务、不拉 Chromium，任务留队列等内存恢复。 |
| 4 | `capture.py` | `_reset_capture_pool()` 超时重建线程池时**主动 `get_web_sandbox().close()`**，用 driver PID 进程树强杀回收卡死的 Chromium，切断内存累积。 |
| 5 | `sandbox/web.py` | 浏览器回收阈值 300 次→60 次、6h→2h，让 Chromium 堆及时释放。 |

### 为什么这样能根治

- **看门狗**解决「内存不够还硬取证」：内存低时主动让路，系统不再进入 D 状态，API 始终有内存响应；
- **超时清理浏览器**解决「重建反而泄漏」：每次超时真正释放旧 Chromium，RSS 不再单调上涨；
- **收紧回收**减少 Chromium 堆的长期增长。

三者合力把「自锁螺旋」改成「负反馈」：内存低 → 暂停取证 → 内存恢复 → 继续取证。

## 长期约束

- 1.9G 内存仍是硬件瓶颈：看门狗让系统「卡不死、能自愈」，但取证吞吐会随内存水位自动降速。
- 彻底提升吞吐仍需**扩容内存或迁移**（用户本次选择仅做代码优化，硬件建议留作后续决策）。
- 生产保留 `SILVER_WORKERS=3`（小机器不该 8 并发），新增 `SILVER_CAPTURE_MIN_FREE_MEM_MB=350`。
