## 三、证据仓实测

### 3.1 固化流程

```
采集 → 明文落盘 → SHA-256 校验 → AES-256-GCM 加密 → 写本地密文
     → 上传 vault-store → 回读校验 → 删除明文 → 追加账本 + 保管链
```

试运行结束时：

- `data/evidence/` **为空**（`SILVER_VAULT_REMOVE_PLAINTEXT=1` 生效）；
- `vault-store/blobs/` 73 个 `.ssv`，无任何明文；
- `vault-store/ledger/` 账本 + 保管链；
- `vault verify`：账本 83 条、保管链 249 条、抽样解密全部通过。

### 3.2 双节点重建（关键验收）

在同一台机器上开第二个数据目录，使用同一把密钥、同一后端，只执行 `vault pull`：

| 指标 | 结果 |
| --- | --- |
| 拉取账本 | 83 条 |
| 重建资产 | 82 |
| 重建证据 | 83 |
| 校验 | `verify ok=true` |
| 耗时 | 约 2 秒 |

**这证明"新设备拉取后拥有全部已有信息"不是设计口号，而是可复现的行为。**
（试运行后增强了账本字段，把 tier/score/verdict 一并带走；新节点不再是一堆"未研判"。）

### 3.3 副本

`replica sync` 首次：事件日志 2,559 字节；证据文件 0（明文已被清理）。
试运行后补了 `sync_vault_blobs()`：副本会连同密文一起复制，避免"机器坏了只剩远端一份"。

## 四、OPSEC 实测

| 检查 | 结果 |
| --- | --- |
| `opsec status` | `enabled=true, proxies=0, fail_closed=true` |
| 可疑目标 `enrich --probe` | **拒绝**：`出站被拒：未配置出站代理，拒绝直连可疑目标` |
| CT / crt.sh / RDAP | 正常（判定为 intel，允许直连） |
| 政务/监管/CA | 命中禁访清单，拒绝 |
| 云元数据 `169.254.169.254` | 拒绝 |
| UA | 浏览器 UA 池，无项目名、无 GitHub 地址 |
| 证据/举报导出 | 统一走 `redact_obj`，自身 IP/主机名/数据目录自动抹除 |

**结论：在"没有代理"的现状下，系统选择了"不主动碰可疑目标"，只做被动发现。
这不是能力缺失，而是策略选择——少抓一条证据，胜过暴露整条链路。**

## 七、结论

1. **可用**：30 分钟连续运行，零重启、零异常、发现/研判/取证/校验全链路通。
2. **广泛**：42,084 条证书、1,222 次命中、107 个资产，覆盖 CT 与 DNS 两条独立路径。
3. **健壮**：单日志失败不影响整体；账本/保管链可定位断点；密文可跨节点重建。
4. **安全**：可疑目标零直连；导出物零自身标识；沙箱无代理直接拒绝。
5. **仍需外部资源**：ICP 服务、出站代理、浏览器/MobSF。这三项不解决，
   "主动探测"和"动态取证"就只能停在代码就绪状态。
