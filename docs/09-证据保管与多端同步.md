# 证据保管与多端同步

> 一句话：**原始证据加密留在私有存储，仓库里只放"能证明它没被改过"的东西；任何一台设备拉到账本就能重建全部历史，并且自己能验证。**

---

## 一、数据到底在哪里

以服务器部署（`SILVER_DATA_DIR=/var/lib/silver-sentinel/data`）为例：

| 位置 | 内容 | 是否含个人信息 | 是否可公开 |
| --- | --- | --- | --- |
| `data/sentinel.db` | 资产、信号、分级、图谱、举报草稿 | 有（域名、账号、话术） | 否 |
| `data/events.jsonl` | 只追加事件日志，逐条哈希链 | 有 | 否（可导出摘要） |
| `data/evidence/` | 明文工作副本；开启 `SILVER_VAULT_REMOVE_PLAINTEXT=1` 后为空 | 有 | 否 |
| `data/vault/blobs/ab/<sha>.ssv` | **AES-256-GCM 密文**，按 SHA-256 内容寻址 | 加密后 | 否（无密钥不可读） |
| `data/vault.key` | 32 字节主密钥（0600） | — | **绝对不能** |
| `data/ledger/<node>.jsonl` | 本节点账本：SHA-256、大小、采集时间、资产标识、哈希链 | 有（资产标识） | 可进**私有**仓库 |
| `data/ledger/custody-<node>.jsonl` | 保管链：采集/加密/上传/下载/导入/校验 | 操作元数据 | 可进私有仓库 |
| `data/ledger/remote/<node>.jsonl` | 其他节点账本副本 | 同上 | 同上 |
| 远端 `vault-store/`（dir/S3/WebDAV/IPFS） | 只有密文 `blobs/` + 账本 `ledger/` | 加密后 | 否 |

**仓库（Git）里应该放什么**：只放 `ledger/*.jsonl` + `SHA256SUMS` + `README.md`。这些是固定证据，不含原始文件、不含密钥，体积以 KB 计。

```bash
silver-sentinel vault export --out ../silver-evidence-ledger
cd ../silver-evidence-ledger && sha256sum -c SHA256SUMS && git add . && git commit -m "ledger: 2026-11 批次"
```

导出的目录长这样：

```
node-375a52dc.jsonl          # 逐条账本，每条带 prev/hash
custody-node-375a52dc.jsonl  # 保管链
SHA256SUMS                   # 上面两个文件的摘要
README.md                    # 校验说明与字段解释
```

## 二、为什么要把"文件"和"证明"分开

如果直接把截图、HTML、APK 提交到 Git：

- 仓库一旦公开，受害者信息、未打码的手机号、身份证照片就跟着泄露；
- Git 历史不可删除，出错无法回收；
- 大文件会把仓库撑爆，克隆一次几百 MB。

反过来，只存哈希也不行：哈希只能证明"我手里这份和你那份一样"，不能证明"这份是什么、从哪来、谁经手"。

所以拆成三层：

1. **密文层**（私有/去中心化存储）：原始字节，AES-256-GCM，内容寻址。
2. **账本层**（可进 Git）：`sha256 + size + captured_at + asset + prev/hash`，逐条链式。
3. **保管层**（可进 Git）：谁在什么时间对哪份证据做了什么（采集、加密、上传、下载、导入、校验）。

三者合起来，才构成可向监管/公安提交的"证据保管链"。

## 三、加密设计

### 3.1 算法与格式

```
密文 = "SSV1" | nonce(12B) | 明文长度(4B) | AES-256-GCM(明文)
AAD  = "SSV1" | sha256(明文) | 明文长度
```

- 每个文件独立随机 nonce，绝不复用；
- AAD 绑定内容哈希与长度：把密文改名、截断、拼接都会解密失败；
- 文件名就是明文的 SHA-256：天然去重、天然内容寻址，换后端不用改账本。

### 3.2 密钥从哪来（三选一，优先级从高到低）

| 方式 | 配置 | 适用 |
| --- | --- | --- |
| 环境变量 | `SILVER_VAULT_KEY=<32 字节 base64>` | 容器/K8s Secret |
| 密钥文件 | `SILVER_VAULT_KEY_FILE=/path/vault.key`（默认 `data/vault.key`，0600） | 单机/服务器 |
| 口令派生 | `SILVER_VAULT_PASSPHRASE=...`，scrypt(n=2^15,r=8,p=1) | 多设备人手一份，靠口令互通 |

初始化：

```bash
silver-sentinel vault init                 # 随机生成，打印一次 base64，请离线抄走
silver-sentinel vault init --passphrase '...'   # 口令派生，多设备用同一口令
```

> 密钥丢失 = 所有密文永久不可读；密钥泄露 = 所有证据等于公开。
> 建议：主密钥离线保存（纸质/硬件密钥），服务器上只放密钥文件；不要把 `vault.key` 放进任何 Git 仓库或云盘同步目录。

### 3.3 本地也不留明文

`SILVER_VAULT_REMOVE_PLAINTEXT=1` 时，推送流程为：

```
读明文 → 校验 SHA-256 → 加密写入 data/vault/blobs → 上传远端 → 回读校验 → 删除明文
```

删除动作本身也写进保管链（`redact-plaintext`），所以"什么时候删的、删的哪份"同样可查。
需要人工复核时用 `vault.materialize(sha256)` 临时还原，不改变账本。

## 四、哈希链与保管链

### 4.1 账本条目

```json
{"v":1,"seq":7,"prev":"<上一条 hash>","node":"node-375a52dc",
 "ts":"2026-11-04T05:00:12.345+00:00",
 "evidence":{"sha256":"7e67…","kind":"apk","size":1548,"ext":".apk",
             "note":"原始安装包","captured_at":"2026-11-04T04:59:58+00:00"},
 "asset":{"kind":"apk","value":"silver-sample.apk","normalized":"silver-sample.apk"},
 "blob":{"backend":"dir","name":"blobs/7e/7e67….ssv","locator":"blobs/7e/7e67….ssv"},
 "hash":"<本条 hash>"}
```

`hash = SHA256(canonical(除 hash 外全部字段))`，`prev` 指向上一条。改一个字、删一条、换顺序，`verify` 会精确到第几行。

### 4.2 保管链条目

```json
{"v":1,"seq":12,"prev":"<上一条>","node":"node-375a52dc",
 "ts":"…","action":"upload","subject":"7e67…","actor":"system",
 "detail":{"backend":"dir","locator":"blobs/7e/7e67….ssv","entry":"<账本 hash>"},
 "hash":"…"}
```

动作类型：`seal`（加密）、`upload`（上传）、`download`（从远端取回）、`import`（写入本地库）、
`reject`（密钥不符/哈希不符，拒绝入库）、`missing`（明文与密文都缺）、`corrupt`（落盘文件被改）、
`redact-plaintext`（删除本地明文）。

### 4.3 校验

```bash
silver-sentinel vault verify            # 账本链 + 抽样解密校验
silver-sentinel vault verify --fast     # 只校验链，不解密
```

返回每个节点的 `entries / head / ok`，以及 `custody` 的链状态。任一环节断裂，`ok=false` 并给出原因。

## 五、多端同步模型

### 5.1 为什么不是"共享一个数据库"

SQLite 放云盘 = 迟早损坏；放 Postgres 公网 = 把整库暴露；用 Git 合并二进制 = 冲突无法解。

采用**每节点一条独立账本 + 内容寻址密文**：

```
节点 A ──写──> ledger/node-A.jsonl ──┐
节点 B ──写──> ledger/node-B.jsonl ──┼──> 共享后端（dir / S3 / WebDAV / IPFS）
节点 C ──写──> ledger/node-C.jsonl ──┘
                  blobs/<sha>.ssv（同名即同内容，重复上传无副作用）
```

- 没有共享文件的并发写，天然无冲突；
- 合并按 `sha256` 去重，同一份证据被两个节点采集只会多一条账本、不会多一份密文；
- 每个节点只追加自己的链，互不干扰，谁的账本断了查谁。

### 5.2 一次同步做什么

```
pull:  列出远端 ledger/*.jsonl → 逐条校验链 → 找出本地没有的 sha256
       → 取密文 → 解密 → 校验 SHA-256 → 写明文 → 建资产/证据行 → 记 download/import
push:  找出本地未入账的证据 → 校验 → 加密 → 本地存密文 → 上传 → 回读校验
       → 追加账本与保管链 → 发布自己的 ledger 文件
```

默认每 `SILVER_VAULT_INTERVAL=120` 秒跑一轮，也可手动：

```bash
silver-sentinel vault sync        # pull + push
silver-sentinel vault push
silver-sentinel vault pull
```

实时性：轮询间隔内最终一致。需要"秒级"时把间隔调小，或在采集回调里调用 `vault.sync_once()`；
不建议做成 WebSocket 推送——那会把"证据仓"变成一个必须常连的在线服务，反而降低可用性。

### 5.3 新设备接入（三步）

```bash
# 1. 拿到同一把密钥（三种方式任选其一）
export SILVER_VAULT_KEY='<base64>'          # 或放 vault.key / 用同一口令

# 2. 指向同一个后端
export SILVER_VAULT_ENABLED=1
export SILVER_VAULT_BACKEND=s3
export SILVER_VAULT_TARGET=https://oss.example.com
export SILVER_VAULT_ACCESS_KEY=...
export SILVER_VAULT_SECRET_KEY=...

# 3. 拉取（首次会把全部历史重建到本地）
silver-sentinel vault pull
silver-sentinel vault verify
```

拉取后本地拥有：全部资产行、全部证据行（哈希链按本地接收顺序重建）、全部密文副本、
全部远端账本副本。也就是说，**新设备不是"看别人的数据"，而是"持有一份完整的、可独立验证的副本"**。

### 5.4 后端选择

| 后端 | 配置 | 特点 | 适用 |
| --- | --- | --- | --- |
| `dir` | `SILVER_VAULT_TARGET=/mnt/private/vault` | 最简单，NFS/另一块盘/rsync 目标均可 | 单机 + 外挂盘 |
| `s3` | `SILVER_VAULT_TARGET=https://oss.example` + AK/SK + bucket | 版本化、跨区复制、生命周期 | 团队/机构 |
| `webdav` | `SILVER_VAULT_TARGET=https://dav.example/vault` | 坚果云/Nextcloud 即可 | 个人多设备 |
| `ipfs` | `SILVER_VAULT_TARGET=http://127.0.0.1:5001` | Kubo RPC，自动 pin；CID 即内容地址 | 去中心化分发 |

IPFS 模式下，账本里的 `blob.locator` 记录 CID：任何人拿到 CID + 密钥就能独立取回并验证，
不依赖你的服务器是否在线。这正是"服务器被攻击也不丢证据"的最终形态。

## 六、灾备与恢复：两套机制别混用

| 机制 | 解决的问题 | 数据形态 | 恢复粒度 |
| --- | --- | --- | --- |
| `replica`（异地副本） | 单机磁盘损坏/勒索 | 原始文件 + 事件日志分片 + DB 快照 | 整机 |
| `vault`（证据仓） | 证据被篡改/单点丢失/多端协作 | 密文 + 账本 + 保管链 | 单条证据 |

两者可以同时开：`replica` 保证"机器没了能起来"，`vault` 保证"证据本身可验证、可携带、可合并"。

恢复顺序建议：

1. 新机装系统 → 部署代码 → 恢复 `vault.key`；
2. `vault pull` 拉回全部密文与账本（此时证据已完整，但资产/信号等分析结果还没有）；
3. 如需完整业务状态，再用 `replica` 的 DB 快照恢复 `sentinel.db`；
4. `vault verify` + `silver-sentinel log verify` 双校验，确认两条链都没断。

## 七、威胁模型与残余风险

| 威胁 | 现状 | 残余风险 | 缓解 |
| --- | --- | --- | --- |
| 服务器被入侵 | 密文 + 账本分离；密钥在本地 | 攻击者拿到密钥即可解密 | 密钥放 KMS/硬件密钥；`vault.key` 不与数据同盘 |
| 云厂商窥探 | 只有密文与对象名 | 对象名含 SHA-256，可做已知明文比对 | 对高敏证据启用 `blobs/` 前缀随机化（后续） |
| Git 账本泄露 | 不含原始文件 | 泄露"我们在关注哪些域名" | 账本仓库设为私有；对外只给单条证明 |
| 密钥丢失 | 无法解密 | 永久失效 | 离线备份 + 分片保管（Shamir，后续） |
| 供应链投毒 | 依赖 PyPI | 依赖被替换 | 锁定版本 + hash 校验（后续） |
| 时序关联 | 上传时间可见 | 可推断采集节奏 | 批量延迟上传 / 随机抖动 |

**账本公开的边界**：账本能证明"某份证据在某个时间点存在且未被改动"，但它也暴露资产标识。
所以默认建议**私有仓库**；需要对外自证时，用 `vault export` 导出单条账本 + `SHA256SUMS`，而不是整库。

## 八、命令速查

```bash
# 初始化与状态
silver-sentinel vault init [--passphrase ...]
silver-sentinel vault status

# 日常
silver-sentinel vault push
silver-sentinel vault pull
silver-sentinel vault sync

# 自证
silver-sentinel vault verify [--fast]

# 交付给第三方（只含账本）
silver-sentinel vault export --out ./ledger-2026-11

# 从别人给的账本目录导入（随后 pull 取密文）
silver-sentinel vault import --src ./ledger-2026-11
```

对应的环境变量见 `.env.example` 的「加密证据仓」段。
