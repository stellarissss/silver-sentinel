# 监控空转与冒充高危识别修复（v1.16.10）

## 用户观察到的现象

1. `#watch` 监控列表里，明显涉诈的站点（如「中稀同心」=`s.qka91.com`，页面公然冒充国务院办公厅做「惠民资金审核记录表」）至今没被识别为高危、没取证上主页。
2. 一批已经关停（域名注销 / NXDOMAIN）的站点仍留在监控里，最新一轮监控也没识别出来。
3. 监控页顶部统计长期是「有变更 0 / 有失败 0」，看起来像在空转；长时间没有新发现。

## 取证过程（生产实测，2026-11-18）

CDP 实地访问 `https://s.qka91.com/`：页面标题「中稀同心 - 中国稀土 惠民资金审核记录表」，正文「审核机构 国务院办公厅」「兑换金额」「预计审核时间72小时」，顶部还有「无障碍」入口（专门面向老人）——**明确涉老诈骗，至今在线**。

联网核实：新华网、中国互联网联合辟谣平台、澎湃等多家权威媒体确认，冒充中国稀土集团 / 国务院部委发放「惠民资金 / 补贴」是官方定性的诈骗手法。

生产库直查（`sentinel.db`）：
- `s.qka91.com`（id=4348）：`claim.verdict=impersonation`、`level=3`、冒充「国务院办公厅」，但 `score=70`、`verdict=suspicious`，被人工确认到 `tier=confirmed` 却因分数低挤不进主页 top8（按 score desc 取前 8，被一堆 95 分站占满）。
- 200 个自动盯防目标里，`capture_state=dead` 有 **81 个**、`failed` 22 个——**过半是死站**，全是 NXDOMAIN。它们的 `last_capture_at` 停在 11-09，但 `watch run` 直到 11-18 仍在复访排队。
- 全部 200 个目标的 `change_count` / `fail_count` **全为 0**。

## 根因

### 根因1：冒充最高国家机关被评分封顶 70

`scoring/reassess.py::_apply_claim` 对所有 `impersonation` 一律 `score = max(score, 70)`，且仅在 `verdict in (insufficient, low)` 时才改判 high_risk。后果：
- 冒充国务院办公厅这种最高权威机构，和冒充一个普通地方局同为 70 分封顶；
- 若原 verdict 是 suspicious，改判条件不成立，留下「70 分却挂 suspicious」的分数-判定不一致（s.qka91.com 正是如此）；
- 70 分按主页排序排不进 top8，涉诈却看不见。

### 根因2：死站无人清出盯防池

- `prune_watch()` 只按 tier 清理，完全不检查 `capture_state`，死站永远留在监控里；
- `reconcile_watch()` 每次 housekeeping 又把 watch/confirmed 全量补回，含死站；
- `MAX_AUTO_WATCH=200` 被死站占满，真正在线的可疑站挤不进自动盯防配额——这是「长时间无新发现」的深层原因。

### 根因3：复访对死站空转

`monitor._run_asset_target()` 只认「资产不存在」才 retire；资产还在、只是判死时，仍每轮 `enqueue(priority=1)` 排队，取证线程再烧一次浏览器得到同一句 NXDOMAIN。而 enqueue 分支固定 `changed=False, error=""`，导致 change_count / fail_count 永远 0，监控页看起来空转。

## 修复（v1.16.10）

| # | 文件 | 修改 |
|---|------|------|
| 1 | `scoring/reassess.py` | `_claim_signals` / `_apply_claim` 区分冒充等级：`level>=3` 或冒充国务院/国务院办公厅的，信号权重 92、`score>=90`、`verdict=high_risk`；普通冒充也修正 verdict 对齐（suspicious→high_risk）。**仍不给 confirmed**——人工终审约束不变。 |
| 2 | `capture.py` | `reconcile_watch()` 查询排除 `capture_state=dead`、配额只算启用目标、支持复活合规的停用目标（避免 uq 唯一约束冲突）；`prune_watch()` 增加死站清理（人工目标不动）。 |
| 3 | `monitor.py` | `_run_asset_target()` 复访前检查 `capture_state=dead`，命中即 retire 目标并写明原因，不再排队。 |

### 部署时发现的隐藏 bug（一并修复）

生产执行 `prune_watch()` 时抛 `sqlite3.IntegrityError: FOREIGN KEY constraint failed`。根因：
`scan_runs.target_id` 外键指向 `watch_targets`，生产 `PRAGMA foreign_keys=ON`，原实现直接
`s.delete(row)` 删除监控目标必然违反外键——而 housekeeping 里这段被 `try/except` 吞掉，
**说明死站清理功能从上线起就从未真正生效过**。改为「停用（enabled=False）+ 写停用原因」
代替删除：保住外键完整、保留巡检历史、且不再被调度捞起。本地 fresh_db 未开外键 primal，
所以单测没暴露——这是"测试环境与生产环境不一致"的典型陷阱，已补对应回归测试。

## 已知遗留 / 长期约束

- **人工终审资产的 verdict 不随提分覆盖**：s.qka91.com 因 `reviewed_by` 非空，机器按既有
  设计只更新分数不覆盖 verdict，故详情页 verdict 仍显示「可疑」，但 tier=已确认、90 分。
  这是「机器不越权改人工结论」的既有约束，不影响排序与取证；如需一致化须单独评估。
- **机器判定的最高档仍是 `high_risk`**；`confirmed` 只能来自人工复核 / 官方通报。
- **死站不删除资产与历史证据**，只停用周期盯防，证据仍可查、可恢复。
- **性能观察**：本次诊断中 `/api/stats` 实测约 25s（v1.16.8 后曾为秒级）。经测 SQL 本身
  最慢项约 4.7s，主因是取证超时重建风暴 + CT/DNS 发现 + 监控并发把 1.9G 内存 / 双核榨满
  （取证线程单线程持续 46% CPU）。这不是本次改动引入，属资源容量问题：建议扩容内存或
  限制后台并发；取证超时本身仍会由目标站异常触发，但 v1.16.9 已能安全回收不再卡死。
