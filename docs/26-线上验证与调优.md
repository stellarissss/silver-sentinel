# 线上验证与调优：三次踩坑与三轮收敛

> 一句话：**种子集上的 0.93 什么都证明不了。**
> 把新判据放到 4,294 条真实资产上跑，第一轮就有 1,123 条已排除资产被"复活"、
> 35 条赌场/盗播/色情站被判成"经营型"准备冷存。这篇记录怎么发现、怎么修、修到什么程度。

## 一、验证方法：拿生产库当测试集

上线前只有 102 条手工种子。它能把特征空间校准到同一口径，但回答不了
"真实的四千条会怎样"。所以写了一个只读重评工具 `tools/eval_production.py`：

```
生产库（只读） → 取已存证据 → 用当前代码重算 → 迁移矩阵
```

三条约束让它可以在服务运行时随便跑：

1. **不写库**：只 `SELECT`，不 `commit`，不改档、不建任务；
2. **复现线上落档规则**：`triage.apply` 的"只升不降"与"dismissed 终态"
   在工具里重写了一遍——否则评估结果会比线上乐观（第一版就吃了这个亏）；
3. **单条失败不中断**：4,294 条里总有几个坏 HTML。

```bash
# 服务器上（用户 silver，不是 root）
runuser -u silver -- env SILVER_DATA_DIR=/var/lib/silver-sentinel/data \
  /opt/silver-sentinel/venv/bin/silver-sentinel eval-production \
  --tier candidate,watch --allow-downgrade
```

从 v1.10.6 起它是内置子命令（`silver_sentinel.evalx`，随 wheel 发布），
不用再往服务器拷脚本。

## 二、三个真实事故

### 事故一：1,123 条已排除资产被"复活"

第一轮跑完，迁移矩阵里赫然写着：

```
dismissed → candidate  1123
dismissed →   cold     1019
```

根因是 `triage.apply` 的档位比较：

```python
rank = {"dismissed": 0, "cold": 1, "candidate": 2, "watch": 3, "confirmed": 4}
if first_time or rank[decision.tier] >= rank[previous]:
    asset.tier = decision.tier      # 恒真
```

`rank(dismissed) = 0`，任何决策都 ≥ 0，所以"是否升级"的判断对已排除资产**恒真**。
平时没暴露，是因为没人跑过全量 `rescore`。而线上有 **901 条早期排除记录没有
`triaged` 标记**（词库误报清理、共享基础设施主机名），`first_time` 也成立。

一次 `rescore --retier --limit 3000` 就会把这一千多条整批拉回候选池——
队列重新被客服站和随机主机名灌满，正是用户最初抱怨的那个现象换了个入口。

修复：`dismissed` 是终态，自动流程不得改写；重新入队只走 `triage.activate()`
（有新证据时）或命中官方通报。

### 事故二：整个判定链静默退化（wheel 漏了 beautifulsoup4）

部署完 v1.10.0，验收脚本 6 项过了 3 项，"客服站判定"和"落地页不被排除"都打勾。
但真实原因是：**服务器 venv 里没有 bs4**，`analyze_html` 抛 `ImportError`，
被 `reassess` 的 `except Exception` 吞掉，返回 `None`。

于是：

- 自称抽取全部返回空 → 冒充判定永远 `neutral`；
- 用途补算在第一行就失败 → 用途永远 `?`；
- 验收第 4 项"落地页未被抑制"因为**判不出用途**而"通过"——假阳性。

`pyproject.toml` 的依赖清单里从头到尾没有 `beautifulsoup4`。本地开发环境早就装了，
所以测试全绿、wheel 装得上、服务起得来，只有功能是空的。

修复三件：

1. `beautifulsoup4>=4.12` 写进主依赖（不是可选依赖——它不是锦上添花，
   缺了主判定链就断）；
2. `claim.py` 改为可选导入：缺 bs4 时保留正则可做的标识码判定，并打 warning；
3. `doctor` 增加**能力探测**（bs4 / sklearn / playwright），只告警不触发重启
   （重启解决不了缺包），验收脚本增加"伪造标识码端到端判定"一项——
   不再用"没被抑制"这种阴性指标做验收。

### 事故三：验收脚本自己跑在空库上

`verify-purpose.sh` 第一次跑 doctor 报"没有心跳、零新资产"。原因是脚本手工调 CLI，
没有加载 systemd 的 `EnvironmentFile`，CLI 落到默认的 `$HOME/data` 空库上。

同样的问题会让 `rescore` "成功"地重算 0 条——比报错更危险。

修复：脚本自动解析 `EnvironmentFile=` 与 `User=`，以服务账号执行
（root 直接跑会写出 root 属主的证据文件，之后 worker 读不了）。

## 三、三轮收敛：谁被降档，降得对不对

每轮都拿降档清单人工核验。这三轮的数字就是"保细"和"保广"的拉锯。

| 轮次 | 改动 | 降档数 | 问题 |
|---|---|---|---|
| 基线 | v1.10.0 | 49 | 混进越南赌场、1xbet、斗鱼体育盗播站群、色情导航站 |
| 第 1 轮 | 「经营型」反证词 + 模型独判不给排除权 | 13 | 色情/盗版站换了词就绕过去了 |
| 第 2 轮 | 站群命名 + 满屏直播 | 27 | 色情站、盗版影视、破解站又冒出来 |
| 第 3 轮 | 色情/盗版/破解词根 | 24 | 达标 |

### 为什么"经营型"这个词本身就是坑

模型的二分类是 `target_shaped（落地页/分发页/表单页）` vs `operational（经营型）`。
赌场、盗播站、色情站的内容量都极大，结构上完全不像落地页，于是被稳稳判进
`operational`——但它们是**黑产在经营**，不是"正经经营"。

所以判断"经营型"不能用结构，得用**反证**。`purpose.GATE_VETO` 列的不是风险词，
而是"这个站不可能是正经经营"的结构性反例：

| 类别 | 例子 | 为什么要单独列 |
|---|---|---|
| 博彩 | casino / 1xbet / cá cược / 娱乐城 | 越南、柬埔寨站的落地页全中文，词库分不高 |
| 盗播 | 体育直播 / 直播中 / 无插件 | 站群首页全是赛事表，没有一句诈骗话术 |
| 色情 | 成人导航 / 看片 / 自拍社区 | 内容量比正规站还大 |
| 盗版影视 | 电影网 / 影片库 | 和正常影视资讯站同构 |
| 灰产中介 | 代办提取公积金 / 套现 / 征信修复 | 模板就是企业官网 |
| 站群命名 | `xx-douyin.cc` / `xx-weixin-qq.top` | 内容里可能一句敏感词都没有 |

站群那条正则特意要求**连字符**：`-qq.cc` 命中，`qq.com` 与 `weixin.qq.com` 不命中。

## 四、落地结果

`verify-purpose.sh --apply` 执行 `rescore --retier`（只处理 candidate/watch
中带正文证据的 633 条，不是无差别重算 3000 条）：

```
重评前  candidate 638  cold 1500  dismissed 2152  watch 2
重评后  candidate 621  cold 1526  dismissed 2152  watch 0
```

用户点名的三站：

| 站点 | 档位 | 分数 | 用途 | 理由 |
|---|---|---|---|---|
| 53kf.com | cold | 50.0 | 客服系统 1.00 | 客服 SaaS，不占高危队列 |
| tuiyijunren.cn | cold | 46.6 | 经营型 0.60 | 资讯门户形态 |
| yige-tech.com | cold | 43.8 | 客服系统 | 建站公司，引用客服 SDK |

watch 从 2 降到 0：53kf 是误报（本该降），`zk-gdrv.duckdns.org` 重算后 28.2 分
落到 candidate（仍命中 OpenPhish，还在队列里）。**盯防档空了不是坏事**——
它说明此前两条都不该在那里。

## 五、运维要点

```bash
# 只读验收（默认）
ssh root@<IP> 'bash /tmp/ss-deploy/verify-purpose.sh'

# 重评并落档
ssh root@<IP> 'bash /tmp/ss-deploy/verify-purpose.sh --apply'

# 评估当前代码会把谁降档（不改库）
silver-sentinel eval-production --tier candidate,watch --allow-downgrade
```

回退开关：`SILVER_PURPOSE_SUPPRESS=0` 重启 worker——用途照常算、照常展示，
只不改档位。

## 六、仍然存在的边界

1. **反诈曝光站天然高分**：`zijinpan.cn`（资金盘曝光网）45 分，满页"跑路/崩盘/
   已立案"，词库分高且用途判不出来。它是无害的，但会占队列前排。
2. **营销落地页被判 landing**：`baidu-ads.com`、`yunshanggroup.cn` 是百度广告
   代理商，模板确实像落地页，不能降。
3. **站群留在候选池**：13 个 `*-douyin.cc` 38.6 分，既不该升 watch（不是涉老），
   也不该降（是黑产）。目前没有第五档可放。
4. **样本仍然小**：真正带正文证据的只有 1,251 条，模型指标的置信区间很宽。
5. **反证词是硬编码**：新增一类黑产就要改一次代码。长期应该把这些词做成
   "排除否决集"，从已排除资产里反向学习。
