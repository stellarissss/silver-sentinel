# v1.16.7 · 失联站点折叠与新线索取证饥饿

## 1. 起因：两句用户反馈，其实是同一个病

> 「目前主页面全是失联站点（我举报的），请你把失联站点折叠即可。另外，请你查看最新情况，为何这么长时间没有新发现？」

CDP 真实浏览器打开生产控制台取证：

- 概览页「风险最高线索」8 张卡片全是 `pk2n84.cn` / `v7qm28.cn` / `xp3v95.cn` …
  同一批 95 分站群，全部标记 **站点失联**，`reviewed_by = 人工审批·CDP浏览器`。
- 线索库首屏 `4473 条折成 2885 项（174 组同源）`，第一行 `pk2n84.cn ×80 同证书 /
  95 / 站点失联`，往下还是同一批失联站。

用户「看不到新发现」不是发现停了，而是**发现的东西被三件事压住**。

## 2. 诊断：发现层一直在跑，问题在展示层和取证层

生产只读取样（2026-11-11）：

| 维度 | 实测 | 结论 |
|---|---|---|
| 资产新增 | 近 6h 621 条、近 24h 1850 条、近 72h 5630 条 | 发现**没有停** |
| `DiscoveryEvent` | 近 24h 8073 条、近 6h 3319 条 | CT / pivot 流水持续 |
| 调度 | DNS 探测每 45s 一轮（`300 个候选，26 个已注册`）；`TaskRun` 每分钟一轮 | 引擎 active |
| 首页排序 | 按 `score desc`，前 60 行 **100% 是 `dead` / `failed`** | 95 分失联站群霸屏 |
| 新资产状态 | 近 24h 新增里 973 条 `pending`、分数全 0；最新 8 个资产 `CaptureTask` 数全为 0 | 没取证 → 没正文 → 没分数 |
| 取证队列 | `CaptureTask`: done 9557 / failed 2626 / queued 5 / running 1 | 队列没积压，说明**不是队列卡死** |

### 2.1 展示层：失联站按分数排永远第一

`capture_state = dead` 132 条 + `failed` 1282 条，其中 active 档 939 条。
用户举报过的那批 95 分站群下线后，`verdict` 仍是 `confirmed`、`score` 仍是 95，
按分数排序必然占满首屏。新资产都是 0 分 `insufficient`，排在几千行之后。

### 2.2 取证层（真 bug）：排序把「复访老站」排在「新线索」前面

`capture.py::backfill()` 的 `order_by` 原本是：

```python
tier_rank,
source_rank,                            # ← 问题在这
(Asset.capture_state == "pending").desc(),
Asset.score.desc(), ...
```

注释写的是「从未取证排在已取证待复访前面」，但 `source_rank` 排在 `pending`
之前，语义正好相反：

- `ip_pool` / `ct_bulk` / `ct_burst` 来源的 `source_rank = 0/1`；
- 新线索大多来自 `pivot`（近 24h 562 条）、`ct_poll`（483 条），`source_rank = 2`；
- `capture_refresh_hours = 24` 让 **3022 条 candidate + 1871 条 cold 的
  `captured` 资产**每天都要复访，复访池无限再生；
- 水位 `target = max(4, capture_batch * 6) = 6`，`due` 实测 5，`room = 1`
  ——每轮只补 1 条，补进去的永远是 0 分复访老站。

模拟 `backfill` 选出的前 8 条：前 4 条是 24h 前的 0 分 `captured` 复访站，
后 4 条是 12:42 的 `pending`；而 15:48~16:00 最新入库的 `pending` 完全排不上。
近 24h 有 **431 条 candidate `pending` 且没有任何 `CaptureTask`**。

结果链条：`没取证 → 没正文 → 0 分 → insufficient → 首屏看不到`，
用户感知就是「很长时间没有新发现」。

### 2.3 发现质量：CT 流里绝大多数与涉老诈骗无关

近 24h 新增 1850 条里 `candidate 1178 / cold 664 / watch 9`，**没有新增
confirmed 或 high_risk**。样例 `santander.gestionauto.cl`、
`intranet.gestionauto.cl`、`pve.fiedelak.dns64.de`、`bitville.dev` 都是正常
证书 SAN / 子域名，词表零命中。这是「捕获目标数远少于全国涉老诈骗总数」
的长期结构性差距，不是本次的代码 bug；需要拓宽外部情报源（urlscan /
举报回流 / 团伙 pivoting）与受众指向判据，不能靠改兜底阈值「悄悄」抬门槛。

另外 `NOISE_HINT` 的 `capture_state="skipped"` 在生产一条都没有：纯噪声资产
仍以 `pending` 落库但 `tier=cold`，而 `backfill` 只查
`confirmed/watch/candidate` 三档，`enqueue()` 又拒绝 `cold`，所以这些资产
永远不会进队列，也永远不会出现在有效线索里。这是设计（省预算）而非故障，
但它让「新增资产数」看起来比实际可研判线索多得多。

## 3. 修复

### 3.1 失联站点折叠（展示层，不改数据）

`grouping.py` 新增 `OFFLINE_CAPTURE_STATES = {dead, failed}`、
`OFFLINE_MEMBER_CAP = 40`、`GROUP_LABELS["offline"]`；`group_row()` 支持
`member_cap` 与 `members_truncated`（真实规模用 `size` 给，诱饵统计仍基于全量）。

`api.py::_collapse_rows(fold_offline=True)` 的两条关键边界：

1. **保留同源依据**：整组失联的组（同证书、同前缀族）仍是原来的组，
   `group_kind` 不变，只加 `group.offline = True` 并**整体沉到列表末尾**。
   把 80 条同证书站群粗暴合成一个「失联」大组会吞掉团伙证据，
   违反「避免误判和漏判」的既定要求。
2. **只有无同源依据的失联散站**才合成 `offline:lost` 大组，成员上限 40。
3. **混合组不沉底**：组里只要还有能取到内容的活站，整组留在前面——
   那批人还在运营，不该被藏起来。
4. `/api/stats` 的「风险最高线索」排除 `dead/failed`，新增 `offline_assets`
   计数；概览页给出可点的提示条跳到线索库。

开关：`/api/assets?fold_offline=0` 或 `?collapse=0`（展开全部）都能绕开。
折叠只影响响应，库里的 `verdict` / `tier` / `capture_state` / `group_key` /
`reviewed_by` 一个都不改（有回归测试钉死）。

前端 `app.js`：折叠行 `offline` 标签、截断成员提示、meta 区失联计数与
「跳到列表末尾」按钮、概览提示条；`style.css` 加 `.offline-note`。

### 3.2 修复取证饥饿

`capture.py::backfill()` 新增 `fresh_rank`（`capture_state=pending` 且
`first_seen >= now-24h` → 0，否则 1），排序改为：

```python
tier_rank,                              # 分级仍最优先（watch 复访比 candidate 首访急）
fresh_rank,                             # 近 24h 首次发现、从未取证：独立通道
(capture_state == "pending").desc(),    # 所有从未取证优先于来源硬度
source_rank,
score.desc(), ...
```

不改水位、不改 `capture_batch`、不改复访规则——只把有限的 `room` 优先
分配给新线索。`watch` 复访仍优先于 `candidate` 首访这条业务规则保留。

## 4. 回归

- 新增 `tests/test_offline_fold.py`（6 例）：同源依据保留、混合组不沉底、
  散站大组与成员截断、开关、概览排除、不改数据。
- 新增 `tests/test_backfill_fresh.py`（3 例）：`room=1` 时新线索抢到配额、
  高分复访老站不能压过新线索、`watch` 复访优先级不变。
- 既有 `test_family_fold.py` 用 `failed` 状态构造前缀族样本，正好验证了
  「失联折叠不能吞掉同证书 / 同前缀族分组」。
- 全量 **554 passed**，`ruff check src tests` 全清。

## 5. 已知限制 / 下一步

- 折叠按 `dead` + `failed` 两个状态判定。`failed` 里混着「取证超时但站点
  还活着」的情况，沉底后可能被忽略；后续可按 `capture_error` 细分
  （`FAILURE_DEAD` 才沉底，网络抖动留在前面重试）。
- 失联组沉底后仍占 `total` 项数；用户翻到最后一页才能看到完整清单。
  meta 区的计数与跳转按钮是目前的缓解手段。
- `room` 常年 1、复访池每天再生：排序修复只能保证「新线索优先」，
  不能提高绝对吞吐。若发现继续涨，需要评估 `capture_batch` /
  `capture_refresh_hours` 与取证并发，别再靠改排序打补丁。
- 发现质量的结构性差距（2.3）需要单独开拓情报源，本轮未动评分规则。

## 6. 生产验收与后续热修（v1.16.8）

v1.16.7 部署后 `/api/stats` 正常，但 `/api/assets` 连续 60s / 150s
`HTTP 000` 挂死。根因不在折叠逻辑，而是 v1.16.6 为修列表 N+1 给查询
无条件加的 `selectinload(Asset.evidence)`：折叠视图要取全量资产分组，
于是 57592 条证据被整体 ORM 化（实测 53s+），叠加 `campaign` 懒加载与
uvicorn 进程内 GIL 竞争后彻底不返回。修复、防回归测试、CDP 前后对比与
「为何没有新发现」的收口结论见
[docs/37 · 列表接口性能退化与 v1.16.8 验收](37-列表接口性能退化与v1.16.8验收.md)。

结论：失联折叠、概览排除失联、可绕开开关、`backfill()` 的 `fresh_rank`
均在生产生效；`/api/assets` 恢复 200（约 6s）；全量 **557 passed**。
